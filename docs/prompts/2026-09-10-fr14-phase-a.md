## 2. Team rulings — settled. Build on these. Do not re-open.

**R1.** The LLM sits behind a port declared in `insight-service`'s **application** layer. Two
adapters: a deterministic stub used by every test, and a LangChain4j adapter for runtime. **No
test may call a live model or touch the network.** Same Ports and Adapters argument as ADR 0001.
This becomes **ADR 0004**.

**R2.** spec-01 §1.1 lists "LangChain4j" with no version or coordinates. The approved entry is
`langchain4j-core` plus **exactly one** provider module. If you conclude that more than one
provider artifact is unavoidable, **HALT and report** — do not choose.

**R3.** `insight-service` has **no domain layer**. `AgentTraceRecord` is a CQRS read model. The
JPA entity and its Spring Data repository live in `infrastructure`; orchestration lives in
`application`. **Do not create a `domain` package in `insight-service`.** Note that `application`
must not import JPA either, so the application-layer trace type and the infrastructure JPA entity
are two different types with a mapper in `infrastructure`.

**R4.** The MVP tool set is **three tools only**: `getBatchDetails`, `getSellThroughRate`,
`proposeMarkdown`. `getMarkdownHistory`, `getMarginFloor` and `queryStorePolicy` are later and
must not appear anywhere — not in the port, not in the registry, not in the prompt text.
spec-02's FR14 table tags `getSellThroughRate` "Week 8"; the team has pulled it into the MVP set.
Update that table row so the specification and the code agree (see D7).

**R5.** The agent **proposes only**. No price writes. No call to `pricing-service`, synchronous or
otherwise. **No margin-floor logic anywhere in `insight-service`** — not a constant, not a check,
not a sentence in a prompt template. The margin floor is enforced in `pricing-service`'s domain
layer under FR11 (spec-01 §1.5, Anti-Corruption Layer). This is the project's central argument and
the report rests on it.

2. **How the trigger is consumed.** `sell-through-risk-detected` is currently

3. **Where `getBatchDetails` obtains unit cost.** `BatchReceivedEvent` carries `unitCost`, but

**D5 — the failing tests.** Written before implementation, every one against the stub. Cover at
least:

*Orchestration* (plain JUnit, application layer)
1. A risk event produces a persisted trace whose tool calls are recorded in call order with
   ascending `sequence`, each carrying arguments and result.
2. A proposal produces exactly one `markdown-recommended` publication, carrying the same
   `agentTraceId` as the trace, and fields matching the trace's final recommendation.
3. The same trigger `eventId` delivered twice yields one trace and one publication.
4. When the agent declines to propose, a trace is still persisted and nothing is published — the
   trace is the audit record, not a by-product of success.
5. The registry exposes exactly the three R4 tool names and no others.
6. The stub is deterministic: the same trigger twice yields an identical tool-call sequence.

*R5 guard* (this one is the report's evidence, so make it mechanical)
7. No type in `insight-service` references `pricing-service`, a margin floor, or a price write.
   Assert over the source tree or the package's types — not over a comment.

*Persistence* (`@DataJpaTest`, which `spring-boot-starter-test` already provides)
8. A trace with several tool calls round-trips with `sequence` order preserved.

*Endpoint* (MockMvc, `AgentTraceApiIntegrationTest`)
9. `GET /api/insight/agent-traces/{agentTraceId}` → 200 for a seeded trace, body matching
   spec-04's `AgentTraceResponse` including `toolCalls` in ascending `sequence`.
10. → 404 for an unknown id, **guarded against a vacuous pass** with the
    `assertThat(result.getHandler()).isInstanceOf(HandlerMethod.class)` assertion and an

11. `MarkdownRecommendedEvent` carries every spec-01 §2.6 field and implements `IntegrationEvent`.
12. Its `occurredAt` serialises as an ISO-8601 string. This is the cheap half of known limitation
