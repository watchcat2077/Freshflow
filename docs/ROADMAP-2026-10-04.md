## How to read a task

Every task has **Why** (what mark it protects), **Done when** (the acceptance test), and
**Steps** small enough to act on without thinking. Owners are a proposal; change them in the
Wednesday meeting, not silently. Tasks marked `Claude` are run in the "build" conversation
window; the prompt to paste is given in the task.

Terminal commands are for **Windows PowerShell 5.1**. Each has a ✅ success signal and a ❌
common failure. Run one line at a time. Never paste Markdown into the terminal.

## The honest time budget

Three days to the tutor review, fifteen to submission. Twenty-seven of the thirty-five
remaining marks are the report, and the report is at zero. If only one thing gets done this
week, it is **Phase 1**: enough draft that Wednesday's review finds structural problems while
there are still twelve days to fix them. A perfect Section 2 and nothing else is worth less
than a complete rough draft.

## What a 90%+ report looks like to the marker

The marker has the specification open beside the report and ticks clauses. A 90% report:

1. **Uses the specification's own words as headings** so every clause is findable.
2. **Shows, not tells.** Every claim about the code points to a file, a snippet, a test name
   or a captured output.
3. **Names its own limitations** (G-3, G-4, G-6, G-7) before the marker finds them.
4. **Explains every place it diverges from the lectures or the reference code** in one
   sentence, with the coordinator's ruling cited where there is one.
5. **Is written by the team.** The specification forbids an AI-generated report. The
   evidence the team draws on may be AI-assisted and must say so.
6. **Has every artefact the specification names**: 12 use cases, 12 activity diagrams, a
   domain model diagram, an architecture diagram, a layered-architecture diagram, a database
   diagram, an ownership table, sample code in 3.3 / 3.5 / 3.6, input and output per user
   story, a README with sample inputs, a signed cover page, Harvard references.
