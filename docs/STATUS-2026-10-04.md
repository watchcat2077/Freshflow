## 1. What the project is, in plain words

A supermarket throws away food that reaches its expiry date unsold. The decision that
prevents that waste is a **markdown**: drop the price early enough that the stock clears,
but never so far that the sale loses money.

FreshFlow watches sales as they happen, works out which batches will not sell out before
they expire, and asks an LLM agent to propose a markdown for those batches. The agent may
only **propose**. Whether a proposal is allowed is decided by a deterministic rule — the
margin floor — inside the pricing service's domain layer.

**That split is the project's central argument:** an LLM is probabilistic, so it may
suggest; a business invariant must be deterministic, so it is enforced in code that cannot
hallucinate. Every architectural decision in this project exists to make that split
visible and provable.

### The four bounded contexts

"Product" means three different things in this business, which is why there are separate
contexts rather than one shared model:

| Context | Service | Port | Sees a product as | Domain pattern |
|---|---|---|---|---|
| Inventory & Batch | `inventory-service` | 8081 | a physical batch with an expiry date | Domain Model |
| Sales | `sales-service` | 8082 | a SKU with a price at the moment of scan | Transaction Script |
| Pricing & Markdown | `pricing-service` | 8083 | a cost-and-margin constraint set | Domain Model |
| Insight | `insight-service` | 8084 | a read-side projection of risk | CQRS read side |

Plus a `contracts` module (Published Language — event records only) and a `pos-simulator`.

## 5. Three decisions that need Andy's ruling before writing starts

**Decision 1 — how many functional requirements go in the report.**
The specification asks for **at least 12**. `spec-02` currently specifies **16**. Each one
in the report owes a use case *and* a UML activity diagram, so 16 costs four more diagrams
than the minimum for no extra marks.

Recommended: present **exactly 12** in Section 2.1 — FR1, FR2, FR4, FR5, FR6a, FR8, FR9,
FR11, FR12, FR13, FR14, FR15. That set contains both real-time stories (FR12, FR13), both
agentic stories (FR14, FR15), and the margin-floor invariant (FR11) that carries the
project's central argument. FR3, FR6b, FR7 and FR10 move to a short "out of scope" note.

**Decision 2 — the second agentic user story.**
Section 2.3 requires at least two. Only FR14 exists. Dr Su ruled on 22 September that one
agent may serve two user stories, but a report that leans on that reads thin. The safer
answer is to build a minimal FR15 end-of-day briefing through the same LLM port that FR14
already uses, which costs roughly half a day rather than a rebuild.

**Decision 3 — the "SQL-like language" wording in §3.5.**
The specification says stream processing queries "e.g. using SQL-like language". We use the
Kafka Streams **DSL**, not ksqlDB SQL. The "e.g." makes SQL an example rather than a
requirement, and the DSL's operators (`filter`, `map`, `groupByKey`, `windowedBy`, `join`,
`aggregate`) are the relational operators under different names. **Confirm this with the
tutor on 7 October** and, either way, write §3.5 so it states the DSL-to-SQL correspondence
explicitly rather than leaving the marker to infer it.

## 7. Architecture decisions that must not be re-opened

These are settled. A new conversation should treat them as constraints, not options.

1. **Four bounded contexts**, because "product" means three different things. Insight is a
   read-side CQRS context. *(L3 slides 29–33)*
2. **Domain layer pattern chosen per context.** Inventory and Pricing use Domain Model;
   Sales uses Transaction Script; Insight has no domain layer today. *(L3 slides 15, 18, 22)*
3. **The margin floor is enforced in pricing-service's domain layer**, never in a controller
   and never in an LLM prompt. The agent may only propose. *(L1 slide 21)*
4. **No shared kernel.** `Money`, `Sku` and `Quantity` are re-declared per context. The only
   shared artefact is `contracts`, a Published Language. *(L3 slide 34; L5 slides 19–21)*
5. **Every event carries `eventId` and a producer-assigned `occurredAt`.** Windowing uses
   `occurredAt`, never Kafka ingestion time. *(L4 slide 37)*
6. **Repository interfaces live in `infrastructure.repository`**, per Dr Guoxin Su's ruling
   of 17 and 22 September 2026. *(L4 slide 34; ADR 0005)*
7. **ADR 0001** — `PriceSnapshotFeed`: sales-service never queries pricing-service
   synchronously.
8. **ADR 0002** — Transaction Script services: write-only single-method persistence ports
   are permitted; aggregate-oriented repositories are forbidden.
9. **ADR 0003** — the velocity baseline is config-seeded, an explicit MVP simplification
   entering through a port.
10. **ADR 0004** — the LLM sits behind a port in the application layer; no test touches the
    network.

### Things never to do

- Add a dependency outside `spec-01` §1.1 without coordinator approval.
- Weaken, edit or delete a test, especially the `HandlerMethod` guards or
  `AntiCorruptionLayerGuardTest`.
- Put a business invariant in a controller.
- Let sales-service call pricing-service synchronously.
- Put JPA annotations on domain classes in inventory-service or pricing-service.
- Introduce aggregate roots or aggregate-oriented repositories in sales-service.
- Skip the `docs/ai-log/` entry, or leave work uncommitted at the end of a session.
