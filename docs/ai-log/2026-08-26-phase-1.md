## 3. Blocking inconsistencies

These make Phase 3 test generation impossible or Phase 4 implementation
specification-violating. Each needs a team ruling.

---

### B-1 — `MarginFloor` has no home in the domain model

**Where**: spec-03 §3 lists `MarginFloor` under "Value Objects" but no entity or
aggregate has a `marginFloor` field. `PriceRule` is `sku`, `basePrice`, `unitCost`,
`category` — nothing else.

**Conflicts with**:
- spec-01 §1.4 lists `MarginFloor` as data *owned and persisted* by `pricing-service`.
- spec-02 FR8: "maintain price rules and margin floors **per SKU and per category**".
- spec-04 `PriceResponse.marginFloorRatio` must be returned by `GET /api/prices/{sku}`.
- spec-03 `MarkdownPlan.activate(MarginFloor floor, ...)` — something must supply `floor`.

**Why blocking**: `GET /api/prices/{sku}` is an MVP-CORE endpoint (FR8) and cannot be
implemented. The margin floor is also the input to the system's single most important
invariant; without a defined storage location and lookup rule the Anti-Corruption Layer
has nothing to enforce.

**Unresolved sub-question**: FR8 says floors are held *per SKU **and** per category*.
Spec-03 defines no resolution order. If a SKU-level floor and a category-level floor
both exist, which wins? This must be stated, not guessed.

**Recommended resolution** (team decision required — I have NOT applied it):
add `marginFloor: MarginFloor` to `PriceRule`, plus a `CategoryMarginFloor` entity keyed
by `category`, and state the precedence rule explicitly as "SKU-level floor overrides
category-level floor; category floor is the fallback".

---

### B-2 — `PERCENT_60` is a valid API value but not a valid domain value

**Where**:
- spec-03 §3: `discountTier | DiscountTier <<VO>> | Enum-like: **20/30/50 percent**`
- spec-04 `CreateMarkdownPlanRequest.discountTier`: `enum: [PERCENT_20, PERCENT_30, PERCENT_50, PERCENT_60]`
- spec-04 `PriceResponse.activeDiscountTier`: `enum: [PERCENT_20, PERCENT_30, PERCENT_50, null]` — 60 absent again

**Why blocking**: the entire 422 margin-floor test case — the one error path the
dev-agent prompt calls out by name for Phase 3 — uses `PERCENT_60`. If `DiscountTier`
admits only 20/30/50, the request cannot be deserialised into a domain value object and
the correct response is **400 Bad Request (unknown enum value)**, not **422 Unprocessable
Entity (margin floor breach)**. The specifications currently mandate two different status
codes for the same request. The Phase 3 test cannot be written until this is settled.

**Recommended resolution**: add `PERCENT_60` to `DiscountTier` in spec-03 and to
`PriceResponse.activeDiscountTier` in spec-04. Rationale: the demonstration needs a tier
that is *structurally legal but economically rejected*, otherwise the 422 path proves
nothing about the domain layer — it would only prove that Jackson rejects unknown enums,
which is a presentation-layer behaviour and would not demonstrate the ACL at all.

### B-3 — `MarginFloorPolicy` returns `boolean` but the 422 contract needs numbers

**Where**:
- spec-03 §3 Domain Service:
  `isBreached(Money basePrice, Money unitCost, DiscountTier tier, MarginFloor floor) : boolean`
- spec-04 `MarginFloorRejection` requires `resultingPrice`, `unitCost`,
  `resultingMarginRatio`, `marginFloorRatio`, and a `message` embedding the computed
  figures: `"Discount tier PERCENT_60 yields margin 0.04, below floor 0.15"`.

**Why blocking**: a `boolean` cannot carry `resultingMarginRatio`. Either the
presentation layer recomputes the margin — which places the margin calculation outside
the domain layer and **violates spec-01 §2.5** — or the domain service signature must
change. The specification as written forces a §2.5 violation. This is the exact class of
defect §2.5 exists to prevent.

**Recommended resolution**: change the domain service to return a value object, e.g.
`MarginAssessment evaluate(Money basePrice, Money unitCost, DiscountTier tier, MarginFloor floor)`
carrying `{breached, resultingPrice, resultingMarginRatio, marginFloorRatio}`. The
presentation layer then maps, and computes nothing.

### B-4 — `markdown-recommended` cannot produce a valid `MarkdownPlan`

**Where**: spec-01 §2.6 key fields for `markdown-recommended`:
`batchId, sku, discountTier, effectiveFrom, rationale, agentTraceId` — **no `effectiveTo`**.
spec-02 FR14 tool signature repeats the omission:
`proposeMarkdown(batchId, tier, effectiveFrom, rationale)`.

**Conflicts with**:
- spec-03 `MarkdownPlan.window : PromotionWindow <<VO>>` = `effectiveFrom, effectiveTo`
- spec-03 Pricing invariant 2: "`effectiveTo` must be after `effectiveFrom`"
- spec-04 `CreateMarkdownPlanRequest` lists `effectiveTo` as **required**

**Why blocking**: `pricing-service` is the declared consumer of `markdown-recommended`.
It cannot construct the aggregate the event is supposed to produce. The agent path
(FR14 into FR11) and the human path (`POST /api/markdown-plans`) therefore do **not**
converge on the same domain operation — which directly undermines FR11's stated
guarantee that the check "applies identically whether the proposal originated from a
human or from the agent".

**Recommended resolution**: add `effectiveTo` to the `markdown-recommended` key fields
and to the `proposeMarkdown` tool signature. Rejected alternative: letting
`pricing-service` default `effectiveTo` (e.g. to batch expiry) — that would put a
pricing decision inside a consumer's defaulting logic and make the two paths genuinely
different, which is the thing FR11 forbids.

### B-5 — `sales-service` has no legal way to learn any price

**Where**: this is a three-way contradiction.

1. spec-02 FR6 `[MVP-CORE]`: sales must apply "the currently active price including any
   live markdown" and record it on the line item.
2. spec-03 §2 `PriceSnapshot` requires `effectivePrice` **and `basePrice`**, maintained
   "from `markdown-applied` and `markdown-expired`".
3. spec-01 §2.6 `markdown-applied` key fields: `markdownPlanId, batchId, sku,
   discountTier, effectiveFrom, effectiveTo`. **No monetary amount of any kind.**
   `markdown-expired`: `markdownPlanId, sku, expiredAt`. Also none.
4. spec-01 §1.3: synchronous REST is permitted **"ONLY for agent tool calls from
   `insight-service` to the other services, and for external API access"** —
   so `sales-service` calling `pricing-service` over REST is *forbidden*.
5. spec-01 §1.3: "Services MUST NOT share a database."

**Why blocking**: there is no permitted channel by which `sales-service` can obtain
`basePrice` for a SKU. It receives a *discount tier* with no price to apply it to, and
no base price to fall back on when no markdown is active. `POST /api/transactions`
(MVP-CORE, on the demonstration path) must return `unitPrice` and `totalAmount` in
`TransactionResponse` and cannot. **FR6 is unimplementable as specified without
violating spec-01 §1.3.**

**Recommended resolution** (team decision required): introduce a `price-rule-published`
topic produced by `pricing-service`, carrying `sku, basePrice, category`, consumed by
`sales` (and `insight`). This preserves §1.3, keeps `pricing-service` the owner of price
data per §1.4, and is consistent with the Published Language pattern already declared
for Pricing to Sales in §1.5. It requires adding one row to spec-01 §2.6.

Rejected alternative: adding monetary amounts to `markdown-applied` alone. That fixes
the marked-down case but leaves the *un*-marked-down case — the overwhelmingly common
one, and the one in spec-04's `singleScan` example — with no price at all.

### B-6 — `MarkdownPlan.activate()` cannot evaluate its own invariant

**Where**: spec-03 §3.

```
activate(MarginFloor floor, Money unitCost) : void   // throws MarginFloorBreach
```

Pricing invariant 1: "A plan may only be activated if **the discounted price** is at or
above the margin floor."

The discounted price is `basePrice x (1 - tier)`. `activate()` receives `floor` and
`unitCost` but **not `basePrice`**. Correspondingly `MarginFloorPolicy.isBreached(...)`
*does* take `basePrice` — so the two declarations in the same section of the same
document disagree about what data the check needs.

**Why blocking**: the aggregate cannot enforce the invariant spec-03 says it enforces.
Any implementation must either change the signature or reach outside the aggregate for
`basePrice`, and the latter would put the calculation in the application layer, breaching
spec-01 §2.5.

**Recommended resolution**: `activate(Money basePrice, Money unitCost, MarginFloor floor, MarginFloorPolicy policy) : void`,
or pass the resolved `PriceRule`. Team's choice; both keep the decision inside the domain.

### B-7 — `[MVP-CORE]` FR6 depends on `[POST-MVP]` FR10

**Where**: spec-02 FR6 acceptance criteria: "Consumes `markdown-applied` **and
`markdown-expired`**, maintains a local price snapshot."

- `markdown-applied` is produced by FR9 — `[MVP-PLUS]`
- `markdown-expired` is produced by FR10 — **`[POST-MVP]`**

This is a direct violation of check 5. An MVP-CORE requirement's acceptance criteria
cannot be satisfied until a POST-MVP requirement is built, so MVP-CORE cannot be
declared complete on its own terms — which is precisely what the tagging system exists
to guarantee.

**Recommended resolution**: split FR6. `FR6a [MVP-CORE]` — apply the base price at scan,
`markdownApplied = false`. `FR6b [MVP-PLUS]` — consume `markdown-applied`.
`FR6c [POST-MVP]` — consume `markdown-expired`. This also aligns FR6 with D7 in the
Week 3 minutes, which defines MVP-CORE as the transaction to `item-sold` to windowed
aggregation to velocity slice and does not include markdown at all.

## 4. Major issues

---

### M-1 — spec-04 places a `[POST-MVP]` endpoint on the demonstration path

`GET /api/batches/{batchId}` is documented as "Implements FR4" — and FR4 is
`[POST-MVP]`. But spec-04's own header states "only endpoints on the 17 August
demonstration path are defined", and spec-02 FR14 marks the `getBatchDetails` tool this
endpoint backs as an MVP tool. Three documents disagree about whether this endpoint is
in MVP scope.

**Recommended**: retag FR4 as `[MVP-PLUS]`, or split out a minimal
`FR4a [MVP-PLUS] — retrieve a single batch by id (agent tool support)` from the fuller
query capability. The endpoint is genuinely needed by FR14, so it cannot simply be
dropped.

---

### M-2 — `effectivePrice` on a Pricing endpoint contradicts the context map

spec-03 §5 (Cross-Context Concept Mapping) is explicit:

| Concept | Sales | Pricing & Markdown |
|---|---|---|
| Price | **Effective price charged** | Base price, discount tier, margin floor |

`effectivePrice` is defined by spec-03 as a **Sales**-context concept, living on
`PriceSnapshot`. spec-04 puts it on `PriceResponse`, returned by `pricing-service`.
Given that §5 is presented as "the evidence for the bounded context boundaries", this is
a leak in the one artefact the report will cite to justify the boundaries.

**Recommended**: either remove `effectivePrice` from `PriceResponse` (leaving basePrice
plus activeDiscountTier, from which the caller derives), or amend §5 to state that
Pricing also computes an effective price and Sales caches it. The first is cleaner; the
second is defensible. Do not leave both documents as they stand.

---

### M-3 — `rationale` is accepted by the API but stored nowhere in Pricing

`CreateMarkdownPlanRequest.rationale` is part of the contract, and spec-01 §2.6 carries
`rationale` on `markdown-recommended`. But `MarkdownPlan` (spec-03 §3) has fields
`markdownPlanId, batchId, sku, discountTier, window, status, origin, agentTraceId,
rejectionReason` — **no `rationale`**. The only class with a `rationale` is
`AgentTraceRecord`, which lives in `insight-service`.

Consequence: for a `HUMAN`-origin plan there is no `agentTraceId` and therefore no trace
record, so the human's stated rationale is silently discarded. FR11 requires rejections
to be "recorded and queryable"; a rejection without its rationale is materially less
auditable, which weakens FR11's contribution to objective O4.

**Recommended**: add `rationale: String` to `MarkdownPlan`.

---

### M-4 — No `markdown-rejected` event; the ACL has no feedback path

FR11 requires that a breaching proposal "is rejected and the rejection recorded". For a
**human** proposal via REST, the 422 response communicates this. For an **agent**
proposal arriving on `markdown-recommended`, there is no synchronous caller — and
spec-01 §2.6 defines no rejection topic. `insight-service` therefore has no way to learn
that its recommendation was refused, and `AgentTraceRecord` can never record the outcome
of the decision it traces.

Related: spec-04 defines **no endpoint at all** for querying markdown plans, so
FR11's "rejection is recorded and **queryable**" has no queryable surface even on the
human path — the 422 body does not include the `markdownPlanId` of the persisted
rejected plan.

This is a substantive gap in the Anti-Corruption Layer story, which spec-01 §1.5 and
spec-02 FR11 both nominate as the project's headline architectural contribution.

**Recommended**: add `markdown-rejected` (producer pricing; consumer insight; key fields
`markdownPlanId, batchId, sku, requestedTier, resultingMarginRatio, marginFloorRatio,
rejectionReason, agentTraceId`) to spec-01 §2.6, and add `markdownPlanId` to the
`MarginFloorRejection` schema. Note the event is a Week 9 concern by the CLAUDE.md
milestone plan, but the spec should record it now.

---

### M-5 — Inventory invariant 4 references data the aggregate does not hold

"`expiryAt` must be after the receipt timestamp." `StockBatch` has no `receivedAt` field;
`receivedAt` is on `GoodsReceipt`, which spec-01 §2.4 classifies as a separate **Entity**,
not part of the `StockBatch` aggregate. The aggregate cannot enforce the invariant.

Separately, spec-04 documents the 400 case as "expiry **in the past**" — a comparison
against *now*, not against a receipt timestamp. These are two different rules.

**Recommended**: restate invariant 4 as "`expiryAt` must be in the future at the time of
creation", enforced in the `StockBatch` factory. That is enforceable inside the aggregate
and matches the API contract.

---

### M-6 — Three Pricing invariants have no documented HTTP status

Phase 3 requires a test for "**every** documented error path". `POST /api/markdown-plans`
documents only `201` and `422`. But invariants 2, 3 and 4 are all reachable from that
endpoint, and there is no defined response for:

- `effectiveTo` at or before `effectiveFrom` (invariant 2)
- unknown `sku` — no `PriceRule` exists, so no `basePrice` and no floor to check against
- re-activating a `REJECTED` plan (invariant 4)

There is also **no `400` response at all** on this endpoint, and no `4xx` documented for
`GET /api/prices/{sku}` beyond a bodyless `404`.

**Recommended**: add `400` with `ErrorResponse` for malformed windows, and `404` for an
unknown SKU, to `POST /api/markdown-plans`. Without this the Phase 3 test suite cannot
claim endpoint coverage.

---

### M-7 — Sales has a business rule but no permitted layer to put it in

spec-03 §2 states a **Rule**: "the price recorded on a `LineItem` is the price in force
at the transaction's `occurredAt`, not the price at the time of processing."

- spec-01 §2.5: "Business invariants live in the domain layer. They MUST NOT be
  implemented in controllers."
- spec-01 §2.3 and spec-03 §2: `sales-service` uses Transaction Script and must **not**
  have aggregates; the application service "orchestrates directly against JPA entities".

So this rule may not live in the controller (§2.5) and has no domain layer to live in
(§2.3). The only remaining home is the application service — which §2.5 does not
authorise.

Compounding this: **spec-01 §2.1 says "Every service follows the four-layer structure"
and shows a mandatory `domain` package, while §2.3 says `insight-service` has NO domain
layer.** §2.1 and §2.3 contradict each other directly.

**Recommended**: amend §2.5 to read: "In Domain Model contexts, business invariants live
in the domain layer. In Transaction Script contexts, they live in the application service.
In neither case may they live in a controller, and in no case may they be delegated to an
LLM prompt." Amend §2.1 to "Every service follows the four-layer structure **except where
§2.3 specifies otherwise**." This preserves the intent of both constraints and removes
the contradiction. **The assessed architecture depends on §2.5 being coherent — this is
worth fixing carefully rather than quickly.**

---

### M-8 — FR12's velocity baseline has no source

FR12 `[MVP-CORE]` requires the windowed count to be compared "against a stored velocity
baseline held in a `KTable`", and `VelocityResponse.baselineVelocity` and
`velocityRatio` are both in the contract. No requirement produces a baseline, no event
in §2.6 carries one, and no endpoint seeds one.

FR12 is MVP-CORE and is the core of the D7 vertical slice, so this must be settled
before Week 5 closes.

**Recommended**: add to FR12 an explicit MVP simplification, mirroring the style already
used elsewhere in spec-02: "**MVP simplification**: baselines are seeded from a static
configuration file at startup into a `GlobalKTable`. Learned baselines are a Week 8
target." A seeded baseline is honest and demonstrable; a computed one is not achievable
in the current milestone.

---

### M-9 — `spring-boot-starter-validation` is not in the permitted dependency list

spec-01 §1.1 is closed: "NO dependency outside this list may be added." The list contains
Spring Web, Spring Data JPA + H2, Kafka, Spring Cloud Stream, Kafka Streams, LangChain4j,
Maven, and `spring-boot-starter-test`.

spec-04 mandates request validation that Bean Validation would normally provide —
`required: [sku, quantity, expiryAt, unitCost]`, `quantity: {minimum: 1}`,
`lineItems: {minItems: 1}` — each with a documented `400` response. Jakarta Bean
Validation ships in `spring-boot-starter-validation`, which is **not** on the list and is
not transitively included by `spring-boot-starter-web` in Spring Boot 3.x.

**This will halt Phase 2 under the dev-agent prompt's own dependency rule.** Raising it
now so the coordinator can be approached before Phase 2 rather than during it.

**Two lawful paths, team's choice**: (a) obtain coordinator approval to add
`spring-boot-starter-validation`; or (b) perform validation by hand in the application
layer and add nothing. Option (b) is fully compliant and arguably better aligned with
§2.5 — validation logic written explicitly is easier to point at in the report than
annotations — but it is more code. I have not chosen; this is a coordinator-facing
decision.

## 5. Minor issues and ambiguities

| # | Issue |
|---|---|
| **N-1** | `MarkdownPlanResponse.discountedPrice` and `PriceResponse.effectivePrice` are derived values with no derivation rule, no rounding rule, and no stated currency-mismatch behaviour. `Money` is "amount + currency" but no spec says what happens when a 30% discount produces a non-representable cent value. | **N-2** | `AgentTraceResponse.toolCalls[].sequence` has no counterpart in spec-03's `AgentTraceRecord`, which says only "ordered list". | **N-3** | `POST /api/markdown-plans` is "Propose **and** activate", yet `MarkdownStatus` includes `PROPOSED` and invariant 3 says "Only a PROPOSED plan may be activated". | **N-6** | **`occurredAt` duplication.** Every event must carry `occurredAt` (§2.6), yet each event also carries a semantically identical domain timestamp: `soldAt`, `changedAt`, `writtenOffAt`, `expiredAt`. Must they be equal? If they diverge, §2.6 says windowing uses `occurredAt` — so `soldAt` becomes a decorative duplicate. Recommend dropping the per-event aliases and using `occurredAt` throughout, or stating explicitly that they are always equal. |

## 6. Cross-cutting concerns raised by CLAUDE.md

Not consistency defects between the four specs, but they affect whether Phase 2 can
begin, so they are recorded here.

**C-1 — The specs' scope tags are anchored to dates that have passed.**
spec-02's legend defines `[MVP-CORE]` as "Must be working by **Friday 15 August**" and
`[MVP-PLUS]` as "Target for **Sunday 16 August**"; spec-04 scopes itself to "the
**17 August** demonstration path". Today is **26 August 2026**, and CLAUDE.md sets the
current milestone as Week 5, ending **Sunday 30 August 2026**. The tags are still useful
as *relative priority ordering*, but their literal deadlines are not actionable. The team
should confirm that the tags now mean priority tiers rather than dates, and ideally
reissue spec-02 with the milestone anchors from CLAUDE.md.

**C-2 — Three demonstration-path endpoints cannot work "against H2" in Week 5.**
CLAUDE.md's Week 5 target is "the demo-path endpoints in spec-04 work against H2", with
Kafka wiring deferred to Week 6 and Kafka Streams to Week 7. But
`GET /api/insight/velocity/{sku}` is defined by spec-04 as "served from the Kafka Streams
state store via Interactive Query", `GET /api/insight/risks` depends on the same
topology, and `POST /api/batches` is required by FR1 to publish `batch-received`.

These are not reconcilable as written. The team needs to rule on which of the following
Week 5 means, before Phase 2 starts:

- **(a)** All eight endpoints exist and return correct shapes, with insight endpoints
  served from a stub/in-memory store and event publication stubbed behind a port
  interface. Phase 3 tests assert HTTP contract only.
- **(b)** Only the four non-streaming endpoints (`/api/batches`, `/api/batches/{id}`,
  `/api/transactions`, `/api/prices/{sku}`) are in Week 5 scope; the three insight
  endpoints and `POST /api/markdown-plans` move to Weeks 6–7.

I recommend **(a)**: it keeps the full API surface honest, lets the Phase 3 test suite be
written once against all eight endpoints as the dev-agent prompt requires, and the port
interfaces are needed for the layering constraint regardless. But this is a scope
decision and I have not acted on it.

**C-3 — Domain events: `contracts` module vs. the "domain imports nothing" rule.**
spec-01 §2.1 places "domain events" inside the `domain` package. §2.6 says "**All** events
are defined in the `contracts` module." §2.2 says the `domain` package "MUST NOT import
from `presentation`, `application`, `infrastructure`, Spring, JPA, Jackson, or Kafka."

If domain classes import event types from `contracts`, they import another Maven module —
which §2.2's list does not literally forbid, but which does make the domain depend on a
shared published language. CLAUDE.md resolves this ("Distinguish internal events within
one bounded context from external integration events across contexts, via Kafka"), but
**spec-01 does not**, and the specs are the authoritative source.

**Recommended**: amend §2.6 to "All **integration** events — those crossing a bounded
context — are defined in the `contracts` module. Internal domain events remain in the
producing service's `domain` package and are translated to integration events in
`infrastructure`." This makes §2.1 and §2.6 consistent and preserves §2.2.
