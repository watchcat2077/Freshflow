### 1.2 `LangChain4jMarkdownDecisionAgent` — the ReAct loop

The adapter behind the R1 port, in `infrastructure`. The loop: system message, user message stating
the risk, then round trips offering the three tool specifications; each tool call is translated,
invoked through the **real** `AgentToolRegistry`, recorded as a `ToolCall` numbered from 1, and
handed back to the model; the loop ends when the model answers without calling a tool, or at
`max-steps`.

Three properties are deliberate and a later reader will want to know so.

**The tool specifications are built from `AgentToolRegistry.toolNames()`**, not from literals. A
tool added or removed in the registry cannot then silently disagree with what the model is told it
may call — R4's cap is enforced in one place and read in the other.

**The proposal is taken only from a `proposeMarkdown` call the registry accepted** (a result
beginning `recorded `). A rejected call is still recorded in the trace, because what the agent
attempted is part of the audit record, but it proposed nothing.

**A model failure is not swallowed.** A tool failure is an answer the model may correct — that is
the ReAct pattern — but an unreachable model, a rejected credential or a timeout propagates out of
`deliberate`. The orchestrator then writes no trace, and at-least-once delivery may retry. The
alternative, catching it and recording a trace, would put a transient outage into the audit record
permanently and spec-06 §5's idempotency check would suppress every retry of it.

**The system prompt carries no downstream invariant.** It states the task, the three tools, the
four tier names and the shape of an answer, and says nothing about what makes a proposal acceptable
to the Pricing context. That is R5 applied to the one new place it could be violated, and
`AntiCorruptionLayerGuardTest` scans string literals, so the prompt is inside the guard rather than
beside it. **The agent must be able to propose something Pricing will reject**; that rejection is
the project's central demonstration and a prompt that prevented it would remove the demonstration.

### 1.3 `MarkdownToolArguments` and the test that pins it

A separate, package-private class translating the model's JSON tool arguments into the flat
encoding `AgentToolRegistry.invoke` reads, and back into a `MarkdownProposal`.

**It is a separate class for two reasons, and the second is the one that matters.** First, the
adapter is then about the loop and nothing else. Second, and decisively: the encoding can be
asserted **without importing LangChain4j into test sources**, which keeps ADR 0004's second
verification check — `grep -r "dev.langchain4j" insight-service/src/test/` returns nothing — true
after this phase exactly as it was before it.

`MarkdownToolArgumentsTest` (6 tests) pins:

- the read tools encode to a bare token, and the registry accepts it;
- `proposeMarkdown` encodes to `batchId,tier,effectiveFrom,rationale` **in that order**;
- a rationale containing commas survives, which is why the free text is last;
- malformed, missing and mistyped arguments produce something the registry **rejects**, never an
  exception;
- an unknown tool name passes through and is answered `error=UNKNOWN_TOOL`.

Every case feeds the encoder's output to a **real** `AgentToolRegistry` over stub ports rather than
comparing it to a literal, because a test that only restated the rule would pass just as happily if
both halves of the contract drifted together.

This is the flag Phase B1 raised as its first item for B2: "load-bearing and asserted by no test".
It is now asserted. See §4.1 for the one part of it that still is not.

### 1.5 `RestBatchDetailsProvider` — spec-06 §3 implemented

Synchronous `GET /api/batches/{batchId}` against `inventory-service`, base URL from
`freshflow.insight.inventory.base-url` (`${INVENTORY_BASE_URL}`, default port 8081), never a
literal. spec-01 §1.3 permits synchronous REST for agent tool calls and for nothing else; spec-04
already names this endpoint as backing the tool.

**What it does when `inventory-service` is unreachable**, which the authorisation asked to be
decided and documented:

| Situation | Answer |
|---|---|
| `404` | `Optional.empty()` — the port's contract: an empty result means the batch is unknown |
| Connection refused, timeout, `5xx`, unparseable body | **The exception propagates** |

The port's javadoc says an empty result "is not an error and must not be turned into one". The
converse is the harder half and is the reasoning here: **an error must not be turned into an empty
result.** An unreachable Inventory is not a batch that does not exist, and rendering it as
`error=BATCH_NOT_FOUND` would hand the agent a false fact it could reason from. Propagating leaves
the trigger un-acknowledged, so redelivery retries once Inventory is back, and no trace is written,
which is correct because nothing was decided.

The response is read into a local record rather than by importing `inventory-service`'s DTO: the
Insight context is a Conformist (spec-01 §1.5), and sharing a presentation type between two
services is the coupling bounded contexts exist to prevent.

**No cache.** Phase B1 flagged that the provider is called twice per deliberation — once by the
tool, once by the orchestrator for `effectiveTo`. Left as two calls deliberately: a cache would have
to choose a lifetime, and the second read is the one the published `effectiveTo` is built from, so
reading it fresh is worth one HTTP round trip on a path that has just spent seconds in a language
model.

### 1.6 `StreamBridgeMarkdownRecommendationPublisher`

`StreamBridge` onto `markdown-recommended`, in the shape `VelocityBaselineSeeder` already uses,
keyed by `batchId` so that Kafka's within-partition ordering keeps one batch's recommendations in
the order they were made. Produced through the message-channel binder, which writes `Instant` as
ISO-8601 and so needs no equivalent of `SellThroughRiskDetectedEventSerde`'s special-cased mapper
(spec-05 §7, G-6).

### 1.8 How the LLM adapter is kept out of every test context

The constraint was that `mvn test` must pass with no environment variable set, and that no test may
construct a live model client. **Two independent guards, either of which would be sufficient:**

1. **`MarkdownAgentConfiguration` is annotated `@Profile("!test")`.** Every test in this service
   runs under `@ActiveProfiles("test")`, so nothing declared in that class is built by any test
   context. The annotation is at class level rather than on a bean, so the guarantee covers whatever
   is added there later.
2. **The model bean is nested inside a `@Configuration` conditional on a non-empty
   `freshflow.llm.api-key`.** With no key there is nothing to build a model from, and the nested
   class is not loaded at all.

Nested rather than bean-by-bean because the condition is then evaluated once for a group of beans
that stand or fall together, rather than in an order Spring does not promise.

**The `markdownAgent` consumer is deliberately outside the key guard**, because
`spring.cloud.function.definition` names it and a definition naming an absent bean fails at startup.
It reaches the orchestrator through an `ObjectProvider`; with no key it logs `[fr14-not-configured]`
once per event and drops the trigger. A service that refuses to start because a credential nobody
needed today is absent would be worse than one that says so.

The consequence at runtime is the one spec-01 §2.7 now records: `insight-service` starts without a
key, serves FR12 and FR13, and simply has no FR14.

## 2. What I assumed that the specifications did not state

**B2-A1 — Spring Boot's Jackson 2.18.2 wins over LangChain4j's declared 2.22, and that is
acceptable.** `langchain4j-core` declares Jackson 2.22; the Spring Boot parent manages 2.18.2 and
takes precedence. Nothing states which should win. I did not override Boot's version, because
pinning Jackson globally to satisfy one library would change serialisation for all six modules.
Checked rather than assumed: `jdeps` against 2.18.2 reports no missing Jackson class, and every
Jackson method the two artifacts reference (`JsonMapper.builder`, `addMixIn`, `propertyNamingStrategy`,
`activateDefaultTyping`, `TypeFactory.withClassLoader` and the rest) exists in 2.18.2. Recorded in
spec-01 §1.1. **It is still a version skew, and §4.4 says why it is on the list of things that could
first fail in B3.**

**B2-A2 — the provider identifier is `google-ai-gemini`.** spec-01 §2.7 requires `provider` to be
injectable and never says what the values are. The string names the adapter in force; it is not
branched on, because the interchangeability is delivered by the port (ADR 0004). The value is the
artifact's own name so that the configuration and the dependency table read the same.

**B2-A3 — `LLM_MODEL` and `LLM_API_KEY` default to empty rather than being required.** spec-01
§2.7's example wrote `model: ${LLM_MODEL}` with no default, which fails placeholder resolution at
startup when unset and would make `insight-service` un-startable without a key. Empty defaults are
what let the FR12/FR13 demonstration run on a machine with no credential, and what let `mvn test`
pass with nothing set. Recorded in spec-01 §2.7.

**B2-A4 — `max-steps` is 8 and `timeout` is 60s.** Neither is specified anywhere. Eight is three
tools plus room to correct a mis-called one twice and still answer. Both are configuration, so
changing them is a YAML edit.

**B2-A5 — the trace's rationale, when the model gives none, says what happened rather than
inventing a judgement.** spec-06 §6 requires a rationale in every outcome and does not say what it
is when a model returns neither a proposal nor closing text. The fallback states the tool-call count
and that nothing was proposed. A blank rationale would make the audit record useless at exactly the
moment it is most needed.

**B2-A6 — the consumer group is `freshflow-insight-markdown-agent`.** Not specified. Named for the
function rather than the service, so a second consumer in this service would not collide with it.

**B2-A7 — `markdown-recommended` is keyed by `batchId`.** spec-01 §2.6 fixes the payload and not
the key. Keyed by the batch so one batch's recommendations share a partition and keep their order;
by SKU would queue unrelated batches behind each other, and by nothing would scatter one batch's
history.

## 3. Deviations from the specifications, with justification

**B2-D1 — spec-06 §4.3's validation row was rewritten, not merely annotated.** The clause said the
tool validates that "`batchId` is the trigger's batch". Phase B1 established that the tool cannot,
and R7 ruled that the orchestrator does. The row now says what the tool actually checks, with R7
stated beneath it. This is a specification change made **under an explicit ruling**, which is the
only basis on which I would make one.

**B2-D2 — the known-limitations section is spec-06 §10, not §7.** R8 asked for it "in the same
format spec-05 §7 uses", and spec-05's known-limitations section is §7. I first took that as a
request for the same *number* and renumbered spec-06's Anti-Corruption Layer section to §7A to make
room. That was wrong, and checking rather than assuming is what caught it: **eight files outside
spec-06 cite "spec-06 §7" meaning the Anti-Corruption Layer**, four of them main-source javadoc and
one of them ADR 0004, which is an accepted decision record I will not edit. The renumber was
reverted. §7 is the Anti-Corruption Layer, as it has been, and the limitations are **§10**, after
the traceability table.

The format is what R8 asked for and the format is what was delivered: statement, consequence,
intended fix, status, under a `G-` heading continuing spec-05's series. A section number that
forces an edit to an accepted ADR is a worse outcome than a section number out of narrative order.

**B2-D3 — spec-01 §2.7's example was changed rather than annotated.** The authorisation asked for
this in terms. The example defaulted the provider to `ollama`, which had become false. A
specification whose example contradicts the configuration it specifies teaches the wrong thing to
whoever reads it next.

## 4. Where I judged something wrong — flagged, NOT acted on

**4.1 — the encoding is pinned; the adapter's *use* of it is not.** `MarkdownToolArgumentsTest`
asserts the translation against the real registry. The line in `LangChain4jMarkdownDecisionAgent`
that calls the translation is exercised for the first time in B3. Closing that gap properly means a
test-source fake `ChatModel`, which means importing `dev.langchain4j` into test sources, which
contradicts ADR 0004's second verification check. **I chose the ADR over the coverage** and am
flagging the choice rather than making it quietly: the team may prefer to amend ADR 0004's check to
"no test constructs a live model client" — which is the property actually wanted — and gain a
scripted end-to-end test of the loop. **Not acted on: it is an ADR change.**

**4.2 — ADR 0004's stated mechanism is now factually wrong, though its guarantee is not.** The ADR
says "the stub lives in test sources precisely so that LangChain4j never reaches the test classpath",
and verification check 1 rests on that. A compile-scope dependency is on the test classpath by
Maven's own rules, so after this phase the library *is* reachable from test compilation. Nothing a
test does has changed — no test source references `dev.langchain4j`, and the two guards of §1.8 are
new and stronger — but a reviewer running the ADR's check against its stated rationale will find the
rationale does not hold. I corrected the equivalent sentence in **spec-06 §1.4**, where it is a
description of the type surface, and **left ADR 0004 alone**, because an accepted ADR is a record of
a decision and amending one is the team's act, not mine. **Flagged.**

**4.3 — R7 and R9 arguably describe the same shape of outcome, and are recorded differently.** R9
exists because `NO_MARKDOWN` was answering two questions with one word: "decided not to" and "tried
and could not". An out-of-scope proposal (R7) is also a run where the agent tried and nothing was
published, and R7 says to record it as declined. I implemented both rulings literally. The case for
leaving it is real — an unresolvable batch is an *environmental* failure this service suffered,
whereas an out-of-scope proposal is a *refusal* this service made — and the case against is that a
supervisor reading `NO_MARKDOWN` cannot tell which happened without reading the tool calls. Recorded
in spec-06 §6 as a note beneath the table. **Flagged; implemented as ruled.**

**4.4 — three things I cannot verify without running them.** Listed here and in §5 because the
authorisation asked for them, and because a phase that produced no live run should say what it has
not shown:

- **Jackson 2.18.2 under LangChain4j 1.20.0** (B2-A1). Class and method references check out; the
  library's own serialisation runs for the first time on the first model call.
- **The message-channel consumer deserialising the Kafka Streams producer's output.** Both ends are
  in this service and use different `ObjectMapper`s — the exact asymmetry that produced G-6. The
  producer's serde writes ISO-8601 and `noTypeInfo()`, and the consumer is Spring Boot's mapper with
  the target type from the function signature, so it should work; it has never been done.
- **Whether the model actually calls the tools.** Tool calling is FR14's single point of failure and
  the Week 3 runbook's S6 said to test it five times before trusting it. That check was against a
  different library version and a different model.

## 5. What B3 needs to know

1. `RUNBOOK.md` **Part B3** is the procedure. It is written to be executed line by line, and §B3.9
   lists the failure modes above with what each looks like from the operator's seat.
2. **`LLM_API_KEY` must be set in the terminal that starts `insight-service`**, not merely somewhere.
   The startup line `FR14: LLM provider=…` is the gate; if it is absent, FR14 is not wired and the
   run will produce FR13 and stop.
3. **The batch arithmetic in §B3.6 is not decoration.** A 60-second window makes one unit look like
   60 an hour, and `hoursToExpiry` truncates, so a batch inside an hour of expiry is never flagged.
   The suggested 400 units at 70 minutes is chosen to flag across a wide range of sales paces.
4. **Keep posting sales for three minutes.** Windows close on stream time, which advances only when
   records arrive. This is G-4 (spec-05 §7) seen from the operator's side.
5. **A trace with no matching `markdown-recommended` is G-7**, not a defect — say so rather than
   debugging it.
