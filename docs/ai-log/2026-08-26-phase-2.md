### 1.3 Package structure — spec-01 §2.1, honouring the §2.3 exceptions

```
com.freshflow.inventory    presentation  application  domain  infrastructure
com.freshflow.sales        presentation  application  domain  infrastructure
com.freshflow.pricing      presentation  application  domain  infrastructure
com.freshflow.insight      presentation  application  ——      infrastructure
```

`insight-service` has no `domain` package, per the §2.3 ruling that the package is
"omitted entirely" for the service designated *No domain layer*.

`sales-service` **does** keep a `domain` package. §2.1's exception clause names two
distinct exceptions and applies them to different services: `insight-service` loses the
package; `sales-service` loses *aggregates*, not the package. §2.3 confirms this — only
`insight-service` is described as having "`presentation`, `application` and
`infrastructure` only". The sales `domain` package is therefore present but deliberately
thin: it will hold `SaleTransaction`, `LineItem` and `PriceSnapshot` as plain data
structures (spec-03 §2), with no aggregate roots and no repository interfaces.

Each layer package carries a `package-info.java` stating that layer's responsibility, its
permitted dependency direction, and the spec clause that governs it. These are the only
`.java` files in the four services besides the bootstrap classes. They serve three
purposes: they keep otherwise-empty packages under version control, they make the
architecture legible at the point where it is easiest to violate, and they give a reviewer
a place to check intent against spec-01. They contain no code.

### 1.4 Bootstrap classes and configuration

Each of the four services has one `@SpringBootApplication` class at the root of its
context package (`InventoryServiceApplication`, `SalesServiceApplication`,
`PricingServiceApplication`, `InsightServiceApplication`) and one `application.yml` giving
its port and an independent in-memory H2 instance:

| Service | Port | JDBC URL |
|---|---|---|
| inventory-service | 8081 | `jdbc:h2:mem:inventorydb` |
| sales-service | 8082 | `jdbc:h2:mem:salesdb` |
| pricing-service | 8083 | `jdbc:h2:mem:pricingdb` |
| insight-service | 8084 | `jdbc:h2:mem:insightdb` |

Distinct in-memory database names, not merely distinct configuration blocks — spec-01 §1.3
forbids a shared database, and `jdbc:h2:mem:testdb` four times over would have been exactly
that within a single JVM. `open-in-view` is disabled so that no persistence context leaks
into the presentation layer; leaving it at its default would let a controller trigger lazy
loading, which is a layering violation dressed up as a convenience.

## 2. What I assumed that the specs did not state

**A-1. Spring Boot patch version — 3.4.1.**
§1.1 says "3.x" and no more. 3.4.1 is the newest 3.x already resident in the local Maven
repository, so the build is reproducible offline. Pinned in the root POM; a team decision to
standardise on a different 3.x is a one-line change.

**A-2. Group ID and version — `com.freshflow` : `0.1.0-SNAPSHOT`.**
`com.freshflow` follows directly from the package root mandated by §2.1. The version is
arbitrary; nothing in the specs fixes one.

**A-3. `pos-simulator` package name — `com.freshflow.possimulator`.**
No spec names it. §2.1's `com.freshflow.<context>` scheme does not strictly apply, because
`pos-simulator` is listed in §1.2 as a *supporting module*, not a bounded context.

**A-4. `pos-simulator` shape — plain Java module, no Spring Boot application, no port,
no datastore, no layered packages.**
It is not a service. §1.2 assigns it no port and §1.4 gives it no data ownership. Making it
a fifth Spring Boot application would have invented topology the specs do not contain. It
has one placeholder `main`. Reversible if the team decides otherwise.

**A-5. `contracts` depends on nothing at all.**
Not stated, but it follows from the pattern: a Published Language shared by four services
must not drag Spring, Jackson or Kafka onto every consumer's classpath. Events will be
plain Java types.

**A-6. `pos-simulator` depends on `contracts`.**
It produces the scan stream, and the scan stream is expressed in the shared contract. Low
confidence but low cost, and easy to drop if the simulator turns out to drive
`sales-service` purely over REST.

**A-7. `ddl-auto: create-drop`.**
Correct for an in-memory database that dies with the process. Not a production setting, and
not one, because §2.8 puts deployment out of scope.

## 3. Deviations from the specs

**D-1. The Kafka, Spring Cloud Stream, Kafka Streams and LangChain4j dependencies from
§1.1 are NOT yet declared.**

This is the one deviation and it is deliberate. §1.1 is a *ceiling* — "NO dependency
outside this list may be added" — not a floor obliging every listed dependency to be
present from day one. Three reasons for deferring:

1. `CLAUDE.md` is explicit: Kafka wiring is Week 6, Kafka Streams is Week 7, the agent is
   Week 9, and "Do not build ahead of the current milestone."
2. It would have broken the milestone. The Spring Cloud Stream Kafka binder auto-configures
   on classpath presence and attempts a broker connection at startup. No broker runs in
   Week 5 (§2.6: "In Week 5 no broker runs"). Declaring it would have put the four services
   into connection-retry noise or outright failure — against the Week 5 target that they
   start cleanly.
3. Spring Cloud Stream needs a `spring-cloud-dependencies` BOM whose version must be
   matched to the Boot version. Choosing that pairing now, five weeks before the first line
   of Kafka code, invites a version mismatch nobody would notice until Week 6.

Each is added in the week that first needs it. No approval is required, because each is
already on the §1.1 list.

**D-2. The §2.7 `freshflow.llm.*` configuration block is not yet in any
`application.yml`.**
§2.7 mandates that the LLM provider be injected through `application.yml`. It belongs to
`insight-service` and nothing reads it before Week 9; LangChain4j is not on the classpath
per D-1. Adding configuration keys that no bean binds would be inert decoration. It goes in
with LangChain4j, and the `${LLM_API_KEY:}` environment-variable indirection of §2.7 will be
honoured verbatim then. Flagged here so it is not lost.

## 4. Where I judge the spec wrong or unclear — NOT acted on

**J-1. §2.1 versus §2.3 on whether `sales-service` keeps a `domain` package.**
§2.1's exception sentence bundles two different exceptions into one clause, and §2.3's
closing line "This is the exception §2.1 refers to" is singular where §2.1 lists two. I read
it as: insight loses the package, sales loses aggregates — and §2.3's own table calling
sales "Transaction Script" rather than "No domain layer" supports that. But the sentence
would be better split. **Suggested wording, for team approval, not applied:** "§2.3
designates two exceptions to the package structure above: `insight-service` omits the
`domain` package entirely; `sales-service` retains it but declares no aggregate roots and no
repository interfaces within it."

**J-2. §1.3 does not say which layer declares `PriceSnapshotFeed`.**
It says the port is "declared in `sales-service`" and stops there. That matters, because
§2.3 forbids repository abstractions in sales' domain, and an inbound port is close enough
to one that the placement is not self-evident. Two defensible homes: `application` (it is a
driving port, and under Transaction Script the application layer is where behaviour lives),
or `domain` (ports-and-adapters convention). I lean `application`. **No decision needed for
Phase 2** — the skeleton declares no interfaces — but it must be settled before Phase 4
implements FR6a. Raising it now rather than discovering it mid-implementation.

**J-3. §1.1's LangChain4j row carries no version and no artifact coordinates.**
Unlike every other row it names no version, and LangChain4j ships as a family of artifacts
(`langchain4j`, `langchain4j-open-ai`, `langchain4j-ollama`, the Spring Boot starters). §2.7
requires hosted and Ollama providers to be interchangeable without code change, which
implies at least two provider artifacts. Whether that counts as one approved dependency or
several is a question for the coordinator. Not urgent — Week 9 — but it will need an answer
before then.
