## 1. What I did

Five classes, nine method bodies, and nothing else. Every rule implemented is one spec-06 already
states; where it did not state one, §2 below records the gap.

### 1.1 `application/AgentToolRegistry` — two bodies

`toolNames()` returns exactly the three constants (R4). `invoke(toolName, arguments)` dispatches on
the name and renders spec-06 §4's answers:

| Tool | Answer | Absent data |
|---|---|---|
| `getBatchDetails` | `batchId=… sku=… remainingQuantity=… expiryAt=… unitCost=… <currency>` | `error=BATCH_NOT_FOUND batchId=…` |
| `getSellThroughRate` | `velocityPerHour=…`, and `baselineVelocity=… velocityRatio=…` only when a baseline is stored | `error=NO_CURRENT_VELOCITY sku=…` |
| `proposeMarkdown` | `recorded batchId=… tier=…` | `error=INVALID_ARGUMENTS …` |

Three properties are worth naming because a later reader will want to know they were deliberate.
**No exception ever leaves `invoke`** — an unknown name, an unparseable argument and an absent batch
are all answers the agent is given and may act on, which is the ReAct pattern working rather than
failing. **An empty velocity is never rendered as zero** (spec-06 §4.2, Phase A assumption A5): the
`Optional` is empty both before a window has closed and after the newest one has aged out, and
neither is a measurement of nothing selling. **`proposeMarkdown` publishes nothing**; it validates
and returns, and the proposal travels back on the `AgentDeliberation` (spec-06 §5).

The tool reads velocity through the real `VelocityQueryService`, so FR12's window-selection ruling
governs what the agent is told, with no second copy of that rule.

### 1.2 `application/MarkdownAgentOrchestrator` — one body

The use case, in the order spec-06 §5 and §6 require:

1. `traceStore.findByTriggerEventId(trigger.eventId())`. Present ⇒ return that trace: no second
   deliberation, no second trace, no second publication.
2. `agent.deliberate(trigger, tools)`, then `completedAt = clock.instant()`.
3. `effectiveTo` from the batch's `expiryAt` through `BatchDetailsProvider` (D-3).
4. The trace, written **whether or not anything was proposed**, with `finalRecommendation` either
   `<TIER> from <effectiveFrom> until <effectiveTo>` or `NO_MARKDOWN`, and the agent's `rationale`
   in both cases.
5. One `markdown-recommended`, published only when there is a proposal, carrying
   `agentTraceId` and `occurredAt = completedAt`.

**All three idempotency mechanisms of spec-06 §5 are in place**, and they are three because each
stops something the others do not:

| Mechanism | Where it is | Status |
|---|---|---|
| The `findByTriggerEventId` check | `onRiskDetected`, first statement | Written in B1 |
| `agentTraceId` = `"TRC-" + triggerEventId` | `TRACE_ID_PREFIX`, applied when the trace is built | Written in B1 |
| `UNIQUE (trigger_event_id)` | `AgentTraceEntity`'s `@UniqueConstraint` | Declared in Phase A, kept; `JpaAgentTraceStore.save` deliberately does **not** pre-empt it with a read |

### 1.3 `infrastructure/AgentTraceMapper` — two bodies

Entity ↔ record, both directions preserving the sequence numbers they are given. The write
direction sets `sequence` from the `ToolCall`, never from the position in the list; the read
direction copies the collection in the order `@OrderBy("sequence ASC")` produced and re-sorts
nothing. `JpaAgentTraceStoreTest` hands the calls in 3, 1, 2 and gets 1, 2, 3 back, which is what
makes the ordering a stored property rather than an artefact of insertion order.

### 1.4 `infrastructure/JpaAgentTraceStore` — three bodies

`save` maps and saves, the calls cascading. `findByAgentTraceId` and `findByTriggerEventId` map back
through `AgentTraceMapper`. See D-2 below for the one thing added beyond the mapping.

### 1.5 `presentation/AgentTraceController` — one body

`findByAgentTraceId(...).map(toDto).map(ok).orElseGet(notFound)` — the same shape as
`VelocityController`. The 404 is answered **by the handler**, which is what the endpoint test's
`HandlerMethod` assertion exists to prove. The DTO mapping is a rename: no computation, and above
all no sort, so a store that lost the order would show it rather than be covered for.

## 2. What I assumed that the specifications did not state

**B1-A1 — an unknown tool name answers `error=UNKNOWN_TOOL toolName=…`.** spec-06 §4 fixes the
wording of the three specified failures and not this one, but `AgentToolRegistry`'s own contract
says an unknown name is a tool failure and not an exception. The wording follows the `error=` form
of the other three.

**B1-A2 — a single-argument tool given a null or blank argument answers
`error=INVALID_ARGUMENTS <tool> expects <argument>`.** Same reasoning: spec-06 names
`INVALID_ARGUMENTS` for `proposeMarkdown` only, and the other two need an answer for the same
situation.

**B1-A3 — `proposeMarkdown`'s arguments are `batchId,tier,effectiveFrom,rationale`, split into at
most four parts.** spec-06 fixes the argument *list*; nothing fixes the *encoding*. Splitting with a
limit of four is what lets a rationale contain a comma, which a written justification will. This is
already the encoding `StubMarkdownDecisionAgent` produces, so B2's adapter must produce it too —
see §5.

**B1-A4 — the published event's `batchId` and `sku` come from the trigger, not from the proposal.**
`MarkdownProposal`'s own javadoc gives the reason for `sku` ("taking it from the trigger rather than
from the model removes one field the model could get wrong"), and `batchId` follows it. Under
spec-06 §4.3's validation the two are the same value; D-1 records why that validation is weaker than
stated.

**B1-A5 — the published event's `eventId` is a fresh random UUID.** spec-01 §2.6 requires a UUID and
says nothing about deriving it. It is not derived from the trigger, because the trace identifier
already carries that lineage and two distinct events should not share an identity.

**B1-A6 — a proposal whose batch cannot be resolved is not published, and the trace records
`NO_MARKDOWN`.** spec-01 §2.6 Table A requires `effectiveTo` on the event and the only source of it
is the batch's expiry, so there is no contract-complete event to publish. The trace is still
written, with the agent's own rationale. See §4.3: `NO_MARKDOWN` is the closest of the two values
spec-06 §6 permits, and it is not a comfortable fit.

**B1-A7 — `JpaAgentTraceStore`'s methods are `@Transactional`.** Not stated anywhere, and it is a
departure from `inventory-service`'s plain adapter. The reason is specific: `toolCalls` is a lazy
`@OneToMany` and the mapper reads it, so a read arriving without a transaction — which is exactly
how the controller will call it once B2 wires the real store — would find the session closed.
`inventory-service`'s aggregate has no lazy association and needs no annotation.

## 3. Deviations from the specifications, with justification

**B1-D1 — `proposeMarkdown` validates that the batch is one this service can see, not that it is
"the trigger's batch".** spec-06 §4.3 states the stronger check. `AgentToolRegistry` cannot make it:
it has no reference to the trigger, its constructor takes `(BatchDetailsProvider,
VelocityQueryService)`, and that constructor is pinned by two test files this phase may not edit.
The implemented check is `batchDetailsProvider.findBatch(batchId).isPresent()`, plus the tier,
instant and non-blank-rationale checks §4.3 also requires.

*The residual gap, stated plainly:* an agent could propose for a different batch that happens to
exist, and the tool would accept it. Nothing downstream would mark down the wrong batch, because the
orchestrator publishes the trigger's `batchId` (B1-A4) — but the trace would then record a proposal
whose batch is not the one published, which is an audit record disagreeing with itself. **I did not
relocate the check to the orchestrator**, which is the one place that knows both values: moving a
validation spec-06 sites in the tool is a design decision, not an implementation one. §4.1 puts it
to the team.

**B1-D2 — `JpaAgentTraceStore.save` does not check for an existing row before writing.** It could,
and a reader may expect it to. It must not: spec-06 §5's third mechanism is the database constraint
precisely because "a rule enforced only by a read-then-write is a rule with a race in it". A
concurrent second delivery is meant to fail on the unique constraint here, and the orchestrator's
own `findByTriggerEventId` already handles the ordinary redelivery without reaching this point.

## 4. Where I judged something wrong — flagged, NOT acted on

**4.1 — spec-06 §4.3 sites a validation the type surface cannot support.** As D-1 sets out, "the
`batchId` is the trigger's batch" is not checkable by a registry with no trigger. Three ways to
close it, for the team: construct the registry per run with the trigger (changes the orchestrator's
dependency and two tests); have the orchestrator refuse to publish, and record as declined, a
proposal whose `batchId` is not the trigger's (no test changes, one new rule); or amend §4.3 to say
what the tool can actually check. **My recommendation is the second** — it is one line, it is in the
only class that knows both values, and it is the same argument D-2 already made for publication
being the orchestrator's job. **Not acted on: it is a spec change either way.**

**4.2 — the trace is saved and the event published in two steps that are not atomic.** A crash
between `traceStore.save` and `publisher.publish` leaves a trace recording a recommendation that
Pricing never received, and the idempotency check will suppress any retry, because a trace now
exists. This is the ordinary dual-write problem and the ordinary answer is a transactional outbox.
No specification mentions it, nothing in FR14's scope requires it, and inventing one here would be
architecture by stealth. **Flagged for the team; not acted on.** B2 should know that the window
exists before the consumer's delivery semantics are decided.

**4.3 — spec-06 §6's `finalRecommendation` table has two values and FR14 has three outcomes.**
Proposed, declined, and — B1-A6 — proposed but not publishable because the batch could not be
resolved. The third is recorded as `NO_MARKDOWN`, which is true of what left this service and
misleading about what the agent did; the rationale on the trace is the agent's, so the record is not
wrong, only terse. A third value, or a sentence in §6 ruling that the case collapses into
`NO_MARKDOWN`, would settle it. **Flagged; not acted on.**

## 5. What B2 needs to know

1. **The tool-call encoding is now load-bearing.** The LangChain4j adapter must render
   `proposeMarkdown`'s arguments as `batchId,tier,effectiveFrom,rationale` and the two read tools as
   a single bare token, or `invoke` will answer `error=INVALID_ARGUMENTS` and the model will loop.
   B1-A3 is the contract between the adapter and the registry, and it is asserted by no test.
2. **`BatchDetailsProvider` is called twice per run** — once by the `getBatchDetails` tool and once
   by the orchestrator for `effectiveTo`. Under spec-06 §3's ruling that is two synchronous
   `GET /api/batches/{batchId}` calls per deliberation. Caching them within a run is a B2 decision;
   B1 deliberately did not build a cache.
3. **`@Transactional` on the store means the consumer thread must not already hold an incompatible
   transaction**, and the trace read the controller performs must go through the bean, not a
   hand-constructed adapter.
4. **The `markdownAgent` consumer must call `onRiskDetected` and ignore the return value or log it.**
   The method is idempotent and returns the existing trace on redelivery, so at-least-once delivery
   needs no handling beyond calling it.
5. **4.2's publication window** should be considered when the binding's acknowledgement mode is set.
