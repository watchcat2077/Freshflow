## 2. What I assumed that the specifications did not state

Each of these is a gap I had to fill to produce a compiling type surface. None is acted on beyond
what spec-06 records, and each is flagged here for the team.

**A1 — `markdown-recommended`'s `occurredAt` is the instant the agent completed its deliberation.**
spec-01 §2.6 requires producer-assigned event time on every event and does not say what that means
for this topic. The alternative was to carry the trigger's `occurredAt` — the end of the velocity
window — which would date the recommendation to a moment before it was made. The instant chosen is
the same one stamped on the trace's `completedAt`, so the two records agree. Note that this topic
is not windowed, so nothing downstream computes on it.

**A2 — the trace identifier is `"TRC-" + triggerEventId`.** spec-04 types `agentTraceId` as a plain
string and illustrates it as `"TRC-0001"`, fixing no format. Deriving it makes a concurrent double
delivery collide on the primary key rather than only on a secondary unique constraint, and makes a
trace traceable back to its trigger by inspection.

**A3 — the tool result rendering is one line of `key=value` pairs.** spec-04 types
`ToolCall.result` as a `String` and says nothing further. The rendering is fixed in spec-06 §4 so
that it is assertable rather than incidental.

**A4 — an absent tool result is reported to the agent, not raised as an exception.** A model that
mis-calls a tool, or asks about a batch that is not there, is told so and may correct itself; that
is the ReAct pattern working rather than failing. `error=BATCH_NOT_FOUND`,
`error=NO_CURRENT_VELOCITY` and `error=INVALID_ARGUMENTS` are fixed in spec-06 §4.

**A5 — an empty velocity is reported as unknown, never as zero.** `findCurrentVelocity` returns an
empty `Optional` both before any window has closed and once the newest closed window has aged out
(spec-02 FR12 ruling 2). Neither is "selling at zero". Rendering zero would tell the agent nothing
is moving and push it towards the deepest discount on the least evidence, which is the fabrication
FR12's 404 exists to prevent. This is the same rule spec-01 §2.7 already states for
`baselineVelocity`.

**A6 — `finalRecommendation` is `"<TIER> from <effectiveFrom> until <effectiveTo>"`, or
`NO_MARKDOWN` when the agent declines.** spec-04 declares the field and gives no format.

**A7 — the JPA entities carry real fields and accessors.** D4 requires every class method body to
throw. A JPA entity is the persistence-layer equivalent of a record, and D4 says records carry
their components; an entity cannot be a record, so the equivalent is fields plus plain accessors.
The behaviour that D4 is actually about — the mapping and the store — does throw. Writing entities
whose accessors threw would have risked the Hibernate bootstrap that all 41 existing tests depend
on, which is the opposite of D4's stated purpose.

## 3. Deviations from the specifications, with justification

**D-1 — `getSellThroughRate` takes `sku` only; spec-02 FR14's table writes
`getSellThroughRate(sku, window)`.** The window size is configuration
(`freshflow.insight.velocity.window-seconds`, spec-01 §2.7) and *which* window counts as current
was settled by team ruling 2 in spec-02 FR12. A caller therefore has no choice to express: a
`window` argument would be one the implementation must ignore, or else a second window-selection
rule standing beside the ratified one. Recorded in spec-06 §4 and flagged in spec-02's tool table.

**D-2 — `proposeMarkdown` does not publish; `MarkdownAgentOrchestrator` does, once per trace.**
spec-02 FR14's table says the tool "Publishes `markdown-recommended`". The effect is the same and
the actor is not. The reason is idempotency: **how many times a language model chooses to call a
tool must not decide how many events cross into another bounded context.** An agent calling
`proposeMarkdown` twice while revising itself — an ordinary thing for a ReAct loop to do — would
otherwise put two proposals in front of Pricing for one batch. Secondly, the event carries
`agentTraceId`, which does not exist until the trace does. Recorded in spec-06 §5.

**D-3 — `effectiveTo` is derived from the batch's `expiryAt`.** spec-02 FR14's tool signature has
no such argument; spec-01 §2.6 Table A requires the event to carry one. Somebody has to decide it,
and a markdown meant to clear a batch before it expires has no work left to do afterwards. The
derivation is made in code rather than asked of the model because it is a policy, and because a
window end the model could choose is a window end the model could choose badly. Recorded in
spec-06 §4.

**D-4 — the `markdown-recommended` contract tests live in `insight-service`, not in `contracts`.**
Their natural home is the `contracts` module, and spec-05 §7's stated fix for G-6 puts them there.
`contracts/pom.xml` declares **no dependencies at all**, deliberately — its description says the
contract "must not drag Spring, Jackson or Kafka into any consumer" — so a test there needs a
`pom.xml` change, which this phase forbids. `insight-service` already has JUnit, AssertJ and
Jackson, and is this topic's producer. The tests are in `com.freshflow.insight.contracts` under
insight's test sources. **When G-6's full fix is built, they should move**, together with a
`test`-scoped decision about `contracts`.

**D-5 — three types were added beyond the eight names the authorisation proposed**, plus two in
`infrastructure`. `AgentDeliberation` is the port's return type; `BatchDetails` is
`BatchDetailsProvider`'s; `DiscountTier` is the enum discussed below. In `infrastructure`,
`AgentTraceJpaRepository` is the Spring Data interface behind the adapter and `AgentTraceMapper` is
"the mapper" the authorisation named. Each is a signature requirement, and none carries behaviour.
Recorded in spec-06 §1.1.

## 4. Where I judged a specification wrong — flagged, NOT acted on

**4.1 — `DiscountTier` now names two different types.** spec-01 §2.4 lists `DiscountTier` as a
value object of the Pricing context. This phase declared a `DiscountTier` enum in `contracts`,
because spec-04 fixes the tier set exactly and a `String` on the event could not hold that
contract — the producer is an agent driven by a language model and the consumer enforces a business
invariant on what it receives. spec-03 §6 rules out a shared kernel, so two types of one name is
the intended outcome rather than an accident, and the `contracts` enum carries no behaviour at all.
It is still a name collision a reader will trip over, and spec-01 §2.4 does not mention it. **A
sentence in §2.4 would fix it. Not written: §2.4 is not in this phase's authorised scope.**

**4.2 — spec-04's `PriceResponse.activeDiscountTier` enumerates only three tiers**
(`PERCENT_20`, `PERCENT_30`, `PERCENT_50`, plus null), while `CreateMarkdownPlanRequest`
enumerates four, including `PERCENT_60`. The two cannot both be right: a plan activated at
`PERCENT_60` would be unrepresentable in the price response that describes it. The `contracts`
enum follows the four-value list, because that is the one the authorisation names and the one a
markdown recommendation must be able to express. **Flagged for a spec-04 correction. Not acted
on.**

**4.3 — spec-01 §1.1 lists "LangChain4j" with no version and no coordinates**, which is why R2 had
to be issued at all. §5 below proposes the exact entries. The same table's "Dependency constraint"
requires subject coordinator approval for anything outside it; LangChain4j is inside it by name and
outside it by coordinate, and the milestone that adds the dependency should close that gap in the
table rather than rely on the name.

## 5. The Phase B dependency, for approval — no `pom.xml` was changed

Phase A added no dependency and changed no `pom.xml`, as instructed. Every test runs against the
stub, which is plain Java. What Phase B would add, per R2 — `langchain4j-core` plus **exactly one**
provider module:

| Coordinate | Scope | Module |
|---|---|---|
| `dev.langchain4j:langchain4j-core:1.0.1` | compile | `insight-service` |
| `dev.langchain4j:langchain4j-ollama:1.0.1` | compile | `insight-service` |

The version would be managed in the **root `pom.xml`'s `<dependencyManagement>`**, beside the other
managed versions, so the two artifacts cannot drift apart; the module poms would then declare the
artifacts without a version, exactly as `insight-service` already declares `contracts` and the
Spring Cloud artifacts.

**Ollama is proposed as the single provider** because spec-01 §2.7's own configuration example
defaults to it (`provider: ${LLM_PROVIDER:ollama}`), and because it needs no API key, which keeps
the "never commit a key" rule trivially satisfied for the demonstration. **This is one provider
module, so R2's HALT condition is not met.** If the team prefers a hosted provider instead, it is a
substitution of one artifact for another, not an addition — spec-01 §2.7's whole point is that the
provider is configuration.

The exact version above should be confirmed against what is actually resolvable at the moment
Phase B runs; the *shape* of the request — core plus one provider, version managed at the root —
is what needs approval now.

`ObjectMapper` built by `Jackson2ObjectMapperBuilder.json().build()`, on the reasoning that this is
the builder Spring Boot uses. It failed: Jackson's own default is the epoch number that G-6 is
about, and Boot's ISO-8601 behaviour comes from a customizer the raw builder does not apply. The
test now takes the application's own autowired `ObjectMapper` from a `@JsonTest` slice. The first
version would have passed against a broken application or failed against a working one; it is a
small illustration of G-6's actual lesson, which is that *which* mapper serialises an event is the
whole question.
