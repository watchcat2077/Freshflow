### 1.2 The vacuous-404 trap, and how it is guarded

Two of the ten cases assert `404`. An unmapped path **also** answers `404`. Written naively,
tests 5 and 10 would have gone **green against a service with no controller whatsoever** — a
false pass at precisely the moment Phase 3 exists to prevent one, and it would have stayed
green through Phase 4 without ever proving anything.

Both are therefore guarded: after asserting the status, each asserts that the request was
dispatched to a `org.springframework.web.method.HandlerMethod`.

```java
assertThat(result.getHandler()).isInstanceOf(HandlerMethod.class);
```

A real controller method returning `404` satisfies this. A missing mapping does not. The guard
demonstrably works — see §3, where both currently fail with
`ResourceHttpRequestHandler`, Spring's static-resource fallback, which is proof that no
controller is mapped.

## 2. What I assumed that the specs did not state

**A-1. Configuration property key names for both seeds.**
spec-03 §2 fixes *which* fields the static source supplies (`sku`, `basePrice`, `unitCost`,
`category`) and spec-03 §3 fixes `PriceRule`'s fields, but **no spec names the property keys**.
I chose:

```yaml
freshflow.sales.price-snapshot-seed[].{sku, base-price, unit-cost, category, currency}
freshflow.pricing.price-rules[].{sku, base-price, unit-cost, category, currency, margin-floor-ratio}
```

Phase 4 must bind to these, or change both the binding and the test resource together. Flagged
in comments in both YAML files.

**A-2. The seeded values themselves.**
`SKU-YOG-1KG`, `basePrice` 4.50 AUD, `unitCost` 2.10 AUD, `category` DAIRY, `marginFloorRatio`
0.15. The SKU and unit cost come from spec-04's `yoghurt` example; `marginFloorRatio` 0.15 is
spec-04's own `PriceResponse` example value. **`basePrice` 4.50 and category DAIRY are
invented** — no spec states a base price for any SKU. 4.50 against a 2.10 cost gives a margin
comfortably above the 0.15 floor, so it does not accidentally constrain the Week 7 margin-floor
work.

**A-3. `currency` as a seed field.**
spec-03 §2 lists `basePrice` and `unitCost` as `Money`, which is amount + currency, but the
static-source row does not break out currency. Seeded explicitly as AUD rather than hard-coding
a default in the implementation.

**A-4. Test-scoped H2 database names** (`inventorydb-test` and so on), so a test run cannot
collide with a running instance of the same service.

### 3.1 Additional check — the tests are not merely failing, they are well-formed

A `404` is returned before Spring parses a request body, so a malformed JSON payload or a wrong
required field would stay invisible until Phase 4 and then look like an implementation bug. I
therefore validated all four distinct request bodies independently of the running application:
every one parses as JSON and carries the fields spec-04's `CreateBatchRequest` and
`CreateTransactionRequest` mark `required`. Response-side `jsonPath` expressions were written
directly from spec-04's `BatchResponse`, `TransactionResponse`, `PriceResponse` and
`ErrorResponse` schemas.

## 4. Deviations from the specs

**D-1. Test 6 posts `quantity: 2`, where spec-04's `singleScan` example and FR6a's Phase 3 note
say to post that example, which uses `quantity: 1`.**
Same payload shape, one field changed. At `quantity: 1`, FR6a's two monetary criteria —
"`unitPrice` equals `PriceSnapshot.basePrice`" and "`totalAmount` is the sum of
`unitPrice x quantity`" — assert the same number, so an implementation that ignored quantity
entirely and set `totalAmount = unitPrice` would pass. At `quantity: 2` the expected total is
9.00 against a 4.50 unit price, and that bug is caught. Trivially revertible if the team wants
the example posted verbatim; I judged a falsifiable test worth more than literal fidelity to an
example.

**D-2. Test 7 asserts only the status code, not an `ErrorResponse` body.**
spec-04 gives `POST /api/batches`'s `400` a `content` block referencing `ErrorResponse`, but
`POST /api/transactions`'s `400` has a description and no `content` block at all. Asserting a
body shape the contract does not promise would be inventing the contract. Tests 2 and 3 *do*
assert `$.error` and `$.message`, because for batches the contract does promise them. See S-3.

## 5. Where I judge the spec wrong or unclear — NOT acted on

**S-1. spec-04's `yoghurt` example is stale: `expiryAt: "2026-08-18T22:00:00Z"` is in the
past.**
Today is 26 August 2026. Posted verbatim, spec-04's own happy-path example violates FR1's
"expiry must be in the future" and must yield `400`, not the `201` the example illustrates. The
same applies to `singleScan`'s `occurredAt: "2026-08-17T09:15:00Z"` and to the two
`markdown-plans` examples, though those are harmless because nothing orders `occurredAt`
relative to now. **Worked around, not fixed**: the tests compute `expiryAt` as `now + 48h` and
`now - 24h`. This is the same class of defect as Phase 1 finding C-1, which re-baselined the
spec-02 legend off dates that had passed; the fix would be to re-baseline spec-04's examples
too, or to express them relatively. Needs a team decision — I did not edit spec-04.

**S-2. spec-04's `400` for `POST /api/transactions` does not mention the unknown-SKU case.**
Its description reads "Validation failed — empty line items or non-positive quantity". FR6a's
final acceptance criterion is unambiguous — "A scan of a SKU absent from the snapshot is a
`400`, never a silent zero price" — so I wrote test 8 against FR6a and did not treat this as a
blocking ambiguity. But spec-04 is the contract the tests are generated from, and it is
currently incomplete on its own terms. **Suggested wording, not applied:** "Validation failed —
empty line items, non-positive quantity, or a SKU absent from the local `PriceSnapshot`
(FR6a)."

**S-3. Inconsistent error-body contracts across the two `400`s.**
`POST /api/batches` `400` returns `ErrorResponse`; `POST /api/transactions` `400` returns an
undescribed body. Both are validation failures produced by the same hand-rolled
application-layer mechanism that spec-01 §1.1 mandates pending the `M-9` coordinator decision.
They should almost certainly return the same shape. This drove D-2 and is worth one line in
spec-04.

**S-4. Neither `404` response defines a body.**
`GET /api/batches/{batchId}` and `GET /api/prices/{sku}` both declare `404` with a description
and no `content`. That is defensible — an empty 404 is normal — but it is what forced the
handler-based guard of §1.2, since there is no body to assert on to distinguish a real 404 from
an unmapped route. Recording it so the guard's presence is understood as deliberate rather than
eccentric.

**S-5. `PriceResponse.activeDiscountTier` has an enum that omits `PERCENT_60`.**
`activeDiscountTier` enumerates `[PERCENT_20, PERCENT_30, PERCENT_50, null]` while
`CreateMarkdownPlanRequest.discountTier` enumerates
`[PERCENT_20, PERCENT_30, PERCENT_50, PERCENT_60]`. Consistent with spec-03 §3's "Enum-like:
20/30/50 percent" and probably deliberate — `PERCENT_60` exists only as the example of a tier
that *breaches* the floor and is therefore never active. Not acted on, does not affect Week 5
(test 9 asserts the field is absent, since no markdown can run), but it will matter in Week 7.
