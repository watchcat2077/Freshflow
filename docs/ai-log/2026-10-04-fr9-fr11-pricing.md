### 1.2 Domain layer — `com.freshflow.pricing.domain`

Every file imports `java.*` only (verified, §1.9). No Spring, JPA, Jackson, Kafka, `contracts`.

| Type | Kind | What it holds |
|---|---|---|
| `DiscountTier` | enum VO | `PERCENT_20/30/50/60` with `percent()`; `fromName(String)` throws `DomainRuleViolation("UNKNOWN_TIER")`. This context's own tier, not the `contracts` enum (spec-03 §6) |
| `MarkdownPlanId` | record VO | `newId()` → `MDP-` + 8 upper-case hex; `of(String)`; non-blank |
| `BatchId` | record VO | non-blank; no `newId()` — Pricing never mints a batch |
| `PromotionWindow` | record VO | invariant 2 in the constructor (`INVALID_WINDOW`); `contains(Instant)` is half-open, start inclusive, end exclusive |
| `MarkdownStatus`, `ProposalOrigin` | enums | as spec-03 §3; `ProposalOrigin.fromName` throws `UNKNOWN_ORIGIN` |
| `MarginFloorAssessment` | record VO | exactly spec-03 §3 (B-3): `basePrice`, `unitCost`, `requestedTier`, `resultingPrice`, `resultingMarginRatio` (scale 4 HALF_UP, fixed on construction), `floor`; `breached()`; `message()` |
| `MarginFloorPolicy` | domain service | `assess(PriceRule, DiscountTier)`; ratio = `(resultingPrice − unitCost) / resultingPrice`, scale 4 HALF_UP. Pure, stateless, registered as a bean by `infrastructure.DomainServiceConfiguration` |
| `MarginFloorBreach` | exception | `extends DomainRuleViolation`, code `MARGIN_FLOOR_BREACH`, carries the assessment |
| `MarkdownPlan` | aggregate root | spec-03 §3 fields + `rationale`, `agentTraceId`, `createdAt`, `discountedPrice`; `propose(...)` → PROPOSED; `rehydrate(...)` for the mapper; `activate(MarginFloorAssessment)`; `expire()`; `reject(String)`; `isInForceAt(Instant)`; `toMarkdownAppliedEvent(Instant)` |
| `MarkdownApplied` | domain event | internal form of `markdown-applied`, in this context's value objects |
| `MarkdownEventPublisher` | outbound port | `publish(MarkdownApplied)`; in `domain` beside `PriceRuleEventPublisher` (ADR 0002; ADR 0005 moved repositories only) |
| `PriceRule` | entity (changed) | gains `priceUnder(DiscountTier)` = `basePrice × (1 − tier/100)`, rounded by `Money`'s HALF_UP to cents — the one place a tier becomes a price. Loses the Week 5 placeholders `effectivePrice()` and `activeDiscountTier()`, which returned the base price and null and whose javadoc promised they would "apply the active plan" |
| `MarginFloor` | VO (javadoc only) | the "deliberately not implemented, do not implement the 422 path" paragraph replaced; the range rule is unchanged |

**How invariant 1 is evaluated** (B-6): `activate` checks, in order, that the plan is not REJECTED
(invariant 4, code `PLAN_REJECTED`), that it is PROPOSED (invariant 3, `PLAN_NOT_PROPOSED`), that
the assessment is for its own tier (`ASSESSMENT_TIER_MISMATCH` — the aggregate cannot recompute the
numbers but can refuse numbers that are not its own), and only then `assessment.breached()`. On a
breach it sets REJECTED and `rejectionReason = assessment.message()` **before** throwing
`MarginFloorBreach`, so the refusal exists as state and not only as an exception. On a pass it sets
ACTIVE and `discountedPrice = assessment.resultingPrice()`.

Nothing in `domain` reads `origin`. That is the mechanical form of FR11's "applies identically
whether the proposal originated from a human or from the agent".

## 2. What I assumed that the specs did not state

| # | Assumption | Where it lives |
|---|---|---|
| A-1 | A promotion window is **half-open**: it contains `effectiveFrom` and excludes `effectiveTo`. FR6b says a scan "after `effectiveTo`" reverts; at the instant itself the markdown is over | `PromotionWindow.contains` |
| A-2 | A selling price of zero (reachable only from a base price of zero) has a margin ratio of **0**, which breaches any positive floor, rather than a division-by-zero error | `MarginFloorPolicy.marginRatio` |
| A-3 | The floor is rendered in the breach message **without trailing zeros**, so a floor read back from its scale-4 column as `0.1500` still reads `0.15`, matching spec-03 and spec-04's example text. spec-03 §7 leaves `MarginFloor`'s scale to the B-3/B-6 work; I settled the rendering in the message rather than normalising the value object | `MarginFloorAssessment.message` |
| A-4 | `resultingMarginRatio` is fixed at scale 4 on construction of the assessment, so a hand-built assessment and a computed one compare equal | `MarginFloorAssessment` |
| A-5 | When two ACTIVE plans for one SKU are both in force (two batches of one product, both marked down), `GET /api/prices/{sku}` reports the **deeper discount**, the lowest price a till has been told to charge | `PriceApplicationService.planInForce` |
| A-6 | `effectivePrice` is the plan's **recorded** `discountedPrice`, not recomputed from the current base price. Replacing a rule by PUT after a plan was activated does not silently reprice a live markdown; the price the event announced is the price shown | `PriceApplicationService.toView` |
| A-7 | `findByAgentTraceId` returns the **first plan by `createdAt`** for a trace, as an `Optional`; a second plan for the same trace can only arise through a race (S-8) | `JpaMarkdownPlanRepository` |
| A-8 | A recommendation with a **null or blank `agentTraceId`** is ignored, not recorded: FR14's acceptance criteria require the trace, and a plan with no trace is unauditable | `MarkdownRecommendedMessageHandler.handle` |
| A-9 | A recommendation the application layer cannot assess — malformed, or for a SKU with no price rule — is **dropped with a WARN**, not persisted. FR11's "rejection is recorded" is about the floor; an unassessable proposal is not a rejection by the floor (see D-4) | same |
| A-10 | `rationale` is bounded at **2000 characters** (the column). Over REST that is a 400; on the consumer the adapter truncates with a WARN rather than losing the recommendation, because the full text is in the agent trace keyed by the same id | `MarkdownPlanApplicationService.RATIONALE_MAX_LENGTH`, `MarkdownRecommendedMessageHandler.fitRationale` |
| A-11 | No rule requires a window to be in the future. spec-03 §3 states only invariant 2; a plan whose window has already passed is accepted, activated, and simply never in force | `PromotionWindow` |
| A-12 | The brief said the live-window assertion should be made against `SKU-YOG-1KG`. I made it against a SKU created by PUT with the same numbers, because the H2 instance is shared across the pricing test classes and `PriceApiIntegrationTest` asserts the seeded SKU at its base price; a live markdown on the seeded SKU would make an existing test order-dependent | `MarkdownPlanApiIntegrationTest` |
| A-13 | `agentTraceId` is **not required** when `origin` is `AGENT` over REST; spec-04 marks it nullable and spec-03 says "set when origin is AGENT" without making it mandatory | `MarkdownPlanApplicationService.validateShape` |
| A-14 | `reject(String)` applies to a PROPOSED plan only, and the reason is required. spec-03 gives the signature without the precondition; an ACTIVE plan's only exit is `expire()` (invariant 3) | `MarkdownPlan.reject` |
| A-15 | `PriceRule.effectivePrice()` and `activeDiscountTier()` were **removed** rather than extended. Their Week 5 javadoc said the entity would "apply the active plan"; doing that would need either a plan reference on the entity or the clock inside the domain. The brief allowed computing the view in the application service; the arithmetic stays in one domain place, `priceUnder` | `PriceRule`, `PriceApplicationService` |
| A-16 | Jackson: `@JsonInclude(NON_NULL)` only on `MarkdownPlanResponseDto`, because spec-04 says `discountedPrice` is "absent" for a rejected plan. `PriceResponseDto` still serialises `activeDiscountTier` as `null` when none is in force; spec-04 marks it `nullable` and the existing test accepts either | `MarkdownPlanResponseDto` |
| A-17 | The `markdown-recommended` consumer group is `pricing-markdown-recommended` and the `markdown-applied` producer is keyed by `sku`, mirroring inventory's durable group and this service's existing `price-rule-published` key | `application.yml` |

## 3. Deviations from the specs, with justification

| # | Deviation | Justification |
|---|---|---|
| D-1 | **`markdownPlanId` is one extra field on the 422 `MarginFloorRejection` body.** spec-04 lists `error`, `sku`, `requestedTier`, `resultingPrice`, `unitCost`, `resultingMarginRatio`, `marginFloorRatio`, `message`; all are present and unchanged | spec-04's own 422 description says the rejection "is persisted as a REJECTED plan and is queryable by its id". Without the id in the response there is no path from the refusal to the record: no endpoint lists plans and the 422 carries no `Location`. The addition is strictly additive. **spec-04 should gain the property; I did not edit spec-04, which was outside my remit** |
| D-2 | `MarkdownPlanRepository` has a fourth method, `findByAgentTraceId`, beyond spec-03 §3's three | Needed for the consumer's idempotency on the trace id (A-7, A-8). spec-03 §3 amended with a dated note, which was the one spec edit the brief permitted |
| D-3 | `DiscountTier` has four members; spec-03 §3's `MarkdownPlan` table still says "Enum-like: 20/30/50 percent" | spec-03's own Value Objects paragraph (4 October) adds `PERCENT_60` and explains why. The table cell is stale, not authoritative (S-2) |
| D-4 | A recommendation for a SKU with no price rule is dropped, not persisted as REJECTED, so it is not queryable | Mirrors the REST path, where spec-04 answers 404 with `ErrorResponse` and persists nothing. "Two entry points to one application service and one domain rule" (spec-04) argues for the same outcome on both. If the team wants unassessable recommendations recorded, `MarkdownPlan.reject(reason)` exists for exactly that and the change is one branch in the handler |
| D-5 | Save-then-publish happens inside one transaction with **no outbox**: the `markdown-applied` event is sent before the transaction commits, so a commit failure after a successful send would announce a plan that was never stored | The same shape as `BatchApplicationService` and `ApplyItemSoldHandler`, and the same decision the team took for FR14 as R8 / spec-06 G-7: a known limitation, not a defect to fix in this milestone |
| D-6 | spec-01 §2.6 Table A lists `markdown-applied`'s key fields without `discountedPrice`; the event carries it | The `contracts` record of 4 October (commit 1e9015f) carries `discountedPrice` and its javadoc says why — the till charges the price Pricing authorised, to the cent. The code follows the contract; Table A is one field behind it (S-6) |
