### 1.3 New: `pricing-service` as the producer of `price-rule-published`

spec-01 §2.6 recorded this contract in Week 5 "so the contract is fixed and reviewable, not so that
it is built now". It is built now. Five pieces, placed by the rules spec-01 §2.3 gives for a
**Domain Model** service:

| File | Layer | Why there |
|---|---|---|
| `PriceRulePublished` | `domain` | The internal domain event, in this context's own value objects |
| `PriceRuleEventPublisher` | `domain` | Outbound port. §2.3's table: for Domain Model services, ports — inbound and outbound — are declared in `domain` |
| `PriceRule.toPriceRulePublishedEvent(Instant)` | `domain` | Which fields the event carries is the domain's answer, not the application layer's |
| `PriceRulePublicationService` | `application` | The use case. Retrieves, delegates, hands to a port. Decides nothing |
| `KafkaPriceRuleEventPublisher` | `infrastructure` | The adapter. Translates to the `contracts` module's `PriceRulePublishedEvent` — the Published Language |

`PriceRuleSeeder` now also triggers the announcement, on `ApplicationReadyEvent` rather than
`@PostConstruct`: seeding is an in-process write and can happen during construction; publishing
crosses a process boundary and must wait for the binder. It *triggers* the use case rather than
implementing it, so infrastructure depends inward on application, per §2.2.

Note the contrast worth having ready for Monday: `pricing-service`'s outbound port is in `domain`
and `sales-service`'s is in `application`. That is not an inconsistency; it is ADR 0001 and ADR
0002 applied — the layer follows the service's §2.3 pattern.

### 1.4 Consumption rules (spec-01 §2.6)

`PriceRulePublishedSnapshotFeed` implements both rules the spec states for this topic:

1. **Deduplicate on `eventId`** — a repeated `eventId` is discarded, whatever its payload says.
2. **Last-write-wins on `occurredAt` per `sku`** — ordering is decided by producer-assigned event
   time. An event that *arrives* later but *happened* earlier does not overwrite a newer price.
   Deciding this by arrival order would be relying on ingestion ordering, which §2.6 forbids.

The class holding those rules imports no Kafka type; `SalesMessagingConfiguration` holds the
binding and no logic. The split is deliberate: it means the rules can be tested without a broker,
and it keeps the transport a detail even inside the layer whose job is transport.

### 1.5 Topics and configuration

Topic names are configuration; no adapter hard-codes a destination.

| Binding | Destination (spec-01 §2.6) | Service |
|---|---|---|
| `batchReceived-out-0` | `batch-received` | inventory |
| `itemSold-out-0` | `item-sold` | sales |
| `priceRulePublished-out-0` | `price-rule-published` | pricing |
| `priceRulePublished-in-0` | `price-rule-published` | sales |

Broker: `${FRESHFLOW_KAFKA_BROKERS:localhost:9092}`. Messages are keyed by SKU.
`freshflow.sales.price-snapshot-seed` is deleted from both `application.yml` and
`application-test.yml`, as spec-01 §2.7's "Week 6 consequence" requires. The `pricing-service`
seed block stays, because §2.7 says it is not retired until FR8's full CRUD arrives.

## 3. What I assumed that the specs did not state

| # | Assumption | Why, and what it would cost to change |
|---|---|---|
| A | Spring Cloud release train **2024.0.0**, imported as a BOM | spec-01 §1.1 lists Spring Cloud Stream with no version. 2024.0.0 is the train for Spring Boot 3.4.x, which is what the root POM pins. Changing it is a one-line property change |
| B | Binding names `batchReceived-out-0`, `itemSold-out-0`, `priceRulePublished-out-0`, `priceRulePublished-in-0` | §2.6 fixes *topic* names, not binding names. Topics are set as `destination` in `application.yml`, so the binding names are internal and renameable |
| C | The `price-rule-published` consumer uses an **anonymous group and replays from `earliest`** | §2.6 gives consumption rules but no group semantics. The local `PriceSnapshot` is a materialised view of the whole topic, not a work queue: every instance needs every event, not a share of them. Replay is safe precisely because §2.6's dedup and last-write-wins rules are implemented |
| D | `pricing-service` republishes every seeded rule **on every start** | No spec says when the producer publishes. With FR8 minimal, the seed *is* the act of publishing. The consumer's dedup rule absorbs the repetition |
| E | Messages are **keyed by SKU** | §2.6 names no keys. One SKU's events stay on one partition, so ordering is not left to chance; Week 7's per-SKU aggregation will want the same key |
| F | Broker address from `${FRESHFLOW_KAFKA_BROKERS:localhost:9092}` | Matches `docker-compose.yml` by default and stays overridable without a code change, in the spirit of §2.7 |
| G | New config key `freshflow.messaging.kafka.enabled`, default true | Not in any spec. Introduced for deviation D1; true everywhere except the integration-test profiles |
| H | Last-write-wins tie-break: **equal `occurredAt` → the later arrival wins** | §2.6 does not say. Any rule is arbitrary at exact equality; this is the conventional reading of "last write wins" |
| I | The seen-`eventId` set is **unbounded in memory** | Acceptable at this scale — one standing rule per SKU. It is a leak under a high-volume topic. Bounding it needs either a cache dependency (not approved) or a hand-rolled window; neither is Week 6 work |

## 4. Deviations from the specs, with justification

**D1 — the spec-04 MockMvc tests do not run against a broker.** Under the `test` profile,
`freshflow.messaging.kafka.enabled` is false, the Kafka adapters are not bound, and the ports are
supplied by test-scope adapters in `src/test/java`.

- *Why:* the canonical fix is `spring-cloud-stream-test-binder` or `testcontainers`. Neither is in
  spec-01 §1.1, and this week's authorisation said "Nothing else". The alternative — requiring
  Docker for `mvn test` — makes the whole suite fail on a machine without a broker, which is worse.
- *Why it is not a weakening:* substituting an adapter behind a port in tests is the same property
  the Week 5 → Week 6 swap relies on. The sales test is in fact **stronger** than it was: Week 5's
  version read a YAML block, whereas it now hands a real `PriceRulePublishedEvent` to the real
  Week 6 adapter through the same ingest method the Kafka binding calls, so the adapter's
  translation, deduplication and ordering logic are all exercised. Only the transport is stubbed —
  and the transport is what section 2 above verifies against the real broker.
- *Action:* RUNBOOK Appendix B question 9 already asks Dr. Su about `testcontainers`. **Recommend
  asking specifically for `spring-cloud-stream-test-binder` (test scope).** With it, the binding
  itself becomes unit-testable and this deviation disappears.

**D2 — comments in `TransactionApiIntegrationTest` were updated.** Its javadoc described a seed
that no longer exists. No assertion, no constant value and no request body changed; the two
constants keep the same values (SKU-YOG-1KG, 4.50). The test file is otherwise untouched.

**D3 — a new class was added to `pricing-service`'s application layer.** The instruction "no
application-layer code may change" governs the *adapter swap*, and it holds exactly: no existing
application-layer file was modified anywhere (see §1.2). `PriceRulePublicationService` implements
a use case that did not exist before this week. Putting the publication orchestration anywhere else
would have been worse: in `infrastructure` it would put a use case outside the layer §2.1 assigns
use cases to; in `domain` it would make the domain depend on a clock and an adapter.

**D4 — the duplicate-discard is logged at INFO, not DEBUG.** Idempotent consumption is a specified
behaviour of this service and worth seeing. The volume is bounded by the handful of standing rules
this topic carries. Revisit if the rule count grows.

**D5 — `spring-cloud-dependencies` was added to the root POM's `dependencyManagement`.** It is a
BOM: it pins versions for the two approved artefacts and contributes no dependency itself.
Reported because it is a new entry in a build file and the dependency constraint is a hard one.

## 5. Where I judge the specs incomplete — NOT acted on, for team decision

**S-1. §2.6 states the dedup and last-write-wins rules only for `price-rule-published`.** The
"Every event MUST carry" clause says `eventId` exists "for idempotent consumption" generally, which
implies every consumer deduplicates. Week 6 has only one consumer, so nothing is blocked. Week 7
adds insight-service as a consumer of `item-sold` and `batch-received`, and will need a ruling:
does every consumer deduplicate on `eventId`, or only the ones §2.6 names? Recommend the former,
and that the sentence be generalised — but not this week, and not without the team.

**S-2. Nothing specifies whether `price-rule-published` should be log-compacted.** It is being used
as a state-transfer topic — the standing price rule per SKU — which is the textbook case for
compaction with the SKU as key, and the keying is already in place. Under default retention a rule
can age off the topic while still being in force, at which point a fresh `sales-service` starts
with an incomplete snapshot until `pricing-service` restarts. Not a problem at demo timescales; a
real gap. Deferred deliberately: it changes topic provisioning, which is infrastructure the team
should agree on.

**S-3. §2.6's consumption rules are stated per `sku`, which presumes ordering that only the key
guarantees.** With `KAFKA_NUM_PARTITIONS: 1` the question is moot today. The spec should say that
events are keyed by the entity the rule is scoped to. Assumption E implements this; the spec does
not require it.

**S-4. §1.1's dependency table has no test-scope provision for messaging.** Every other stack
element is testable with what the table allows; Spring Cloud Stream is not. See D1.

**S-5. `price-rule-published` carries no `marginFloorRatio`.** Correct for Week 6 —
`sales-service`'s `PriceSnapshot` (spec-03 §2) does not hold one, and the margin floor is
`pricing-service`'s invariant to enforce (§2.5), so exporting it would invite the wrong service to
check it. Recording it only because FR6b and the Week 7 markdown events will revisit what Sales
needs to know. No change proposed.
