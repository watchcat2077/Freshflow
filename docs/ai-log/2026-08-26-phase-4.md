### 1.2 How the hard constraints were met

**The domain imports nothing.** Across all 22 domain classes in three services, the complete set
of distinct imports is seven JDK types: `java.math.BigDecimal`, `java.time.Duration`,
`java.time.Instant`, `java.util.List`, `java.util.Objects`, `java.util.Optional`,
`java.util.UUID`. No Spring, JPA, Jackson or Kafka, and no import of another layer. Verified
mechanically in §5, not by inspection.

**Persistence ignorance.** `StockBatch` and `PriceRule` carry no JPA annotation. Each has a
separate JPA entity and a mapper in `infrastructure` (`StockBatchMapper`, `PriceRuleMapper`).
`status` is persisted as a `String` rather than as the domain enum, so the persistence model
carries no domain type at all.

**Repository interfaces in `domain`, implementations in `infrastructure`.**
`StockBatchRepository` and `PriceRuleRepository` are declared in `domain` and implemented by
`JpaStockBatchRepository` and `JpaPriceRuleRepository`. The application layer is wired to the
domain interface and never sees Spring Data.

**Invariants in the domain, never in a controller.** `StockBatch.receive` enforces FR1's two
rules — quantity must be positive, expiry must be after the receipt instant — and there is no
path to a `StockBatch` that bypasses it. `PriceRule.of` rejects a currency mismatch and a base
price below cost. Neither controller contains a single conditional that inspects a business
value; both only translate an `ApplicationResult` or an `Optional` into a status code.

**Event publishing as an outbound port with a logging adapter.**
`DomainEventPublisher` (inventory, declared in `domain`) and `SaleEventPublisher` (sales — see
deviation **V-1**) are bound to `LoggingDomainEventPublisher` and `LoggingSaleEventPublisher`.
Each translates the internal domain event into the `contracts` module's integration event before
logging it, mints `eventId` at publication, and carries `occurredAt` through from the producer
rather than reading a clock — spec-01 §2.6 requires producer-assigned event time and forbids
relying on ingestion time. **No Kafka.** No broker dependency, no binder, no topic client.

**No new dependency.** The four already declared are unchanged. Validation is hand-rolled in the
application layer per spec-01 §1.1's interim M-9 ruling; no DTO carries a validation annotation.

**Not built, deliberately.** `MarkdownPlan`, `MarginFloorPolicy` and the 422 path (spec-03 §3
says "Do not implement the 422 path until this is settled" — findings B-3 and B-6, Week 7);
`FefoDeductionPolicy`, `GoodsReceipt`, `WriteOffRecord` (FR2/FR3, `[POST-MVP]`); everything in
`insight-service`. `StockBatch.deduct` exists because it is an invariant of the aggregate, but
nothing calls it and no FR2 use case is wired.

## 2. Deviations from the instructions given — read this section

Three of the Phase 4 constraints, applied literally, would have contradicted spec-01. In each
case I followed the specification and am flagging the divergence rather than burying it.

**V-1. `SaleEventPublisher` is declared in `sales-service`'s APPLICATION layer, not its domain
layer.**
The instruction was "Event publishing is an outbound port in the domain layer". That is what was
done in `inventory-service`, which is Domain Model. For `sales-service` it collides with the
other constraint in the same instruction — Transaction Script, and ADR 0001, which put this
service's ports in `application`. Declaring the inbound port (`PriceSnapshotFeed`) in
`application` and the outbound port in `domain` would split one service's ports across two
layers on no principle, and would put an interface into a domain package whose agreed
description is "plain data structures only". The two Domain Model services keep their publisher
port in `domain`, where their behaviour is. **Reversible in one file move if the team prefers
the literal reading.**

**V-2. `SaleTransactionRecorder`, a one-method outbound port in `sales-service`'s application
layer, persists the transaction.**
The instruction said "no repository abstractions". This is adjacent to one, so it needs
defending. spec-03 §2 says the Sales application service "orchestrates directly against JPA
entities" — but those entities must live in `infrastructure` (a domain package may not import
JPA), so orchestrating directly against them would make `application` depend on
`infrastructure`, against spec-01 §2.2, which is a HARD CONSTRAINT. **spec-03 §2 and spec-01
§2.2 cannot both be satisfied literally.** I resolved in favour of §2.2 and kept the abstraction
as narrow as it can be: write-only, one method, no `findById`, no query, no aggregate behind it.
FR7 — query transaction history — is `[POST-MVP]`, so nothing reads these rows back this week
and no read method is offered. Recorded as finding **F-2** below.

**V-3. `sales-service`'s business invariants are enforced in the application layer.**
The instruction said "Business invariants live in the domain layer, never in controllers".
spec-01 §2.5's table is explicit that for a Transaction Script service they live in "the
**application service** layer &mdash; §2.3 forbids aggregates here, so the transaction script is
the enforcement point". I followed §2.5. The operative half of the instruction — never in a
controller — holds without exception in all three services.

**V-4. The `contracts` module gained three classes.**
`BatchReceivedEvent`, `ItemSoldEvent`, `MoneyPayload`. Not "building ahead": spec-01 §2.6
requires that all events be defined in `contracts`, and the logging adapters need something to
publish. `MoneyPayload` exists because the events carry amounts and spec-03 §6 forbids a shared
kernel, so no context's `Money` may cross a boundary. No Kafka annotation, binding or serialiser
is present.

## 3. What I assumed that the specs did not state

**A-1. Identifier formats** — `BAT-`, `TXN-`, `LI-` prefixes plus 8 hex characters. spec-04
illustrates `BAT-0001` and `TRC-0001` but fixes no format; the tests require only that
`batchId` be non-empty and round-trip.

**A-2. Error codes in `ErrorResponse.error`** — `QUANTITY_NOT_POSITIVE`,
`EXPIRY_NOT_IN_FUTURE`, `EMPTY_LINE_ITEMS`, `UNKNOWN_SKU`, `VALIDATION_FAILED`. spec-04 gives
`ErrorResponse` an `error` field with no enumeration. Codes are minted in the domain
(`DomainRuleViolation.code()`) so the outer layers transport a verdict rather than re-deciding
one.

**A-3. `Clock` is an injected bean.** Domain classes never ask what time it is; every rule
needing an instant is handed one. That is what keeps `StockBatch` deterministic without a clock
abstraction of its own, and it is why a fixed-clock test can be written in a later phase without
touching the domain.

**A-4. `occurredAt` falls back to now when the caller omits it.** spec-04 does not mark it
required on `CreateTransactionRequest`. The fallback is the producer assigning event time, which
is what spec-01 §2.6 demands; it is never taken from ingestion.

**A-5. `PriceRule.effectivePrice()` returns the base price**, and `activeDiscountTier()` returns
null. spec-03 §2: where no markdown is in force the effective price equals the base price — "the
only case that exists in Week 5". The caller asks the domain rather than reading `basePrice`
directly, so Week 7 changes one method body instead of every call site.

**A-6. `PriceRule.of` rejects a base price below unit cost** and a currency mismatch. Neither is
stated in spec-03. Both are conservative and neither is the margin-floor rule, which remains
unimplemented pending B-3.

## 7. Findings — NOT acted on

**F-1. `BigDecimal` scale is inconsistent between the write path and the read path.**
`POST /api/batches` returns `"amount":2.10`; `GET` of the same batch returns `"amount":2.1000`,
because the value has round-tripped through a `scale=4` column. Likewise `4.5000` and `0.1500`
from pricing. Numerically identical, and no test is affected — both parse to the same double —
but the same field renders differently depending on which path produced it, which will look like
a defect to anyone reading the API. Not fixed, because the fix is to decide a currency scale, and
that is a modelling decision spec-03 does not make: not every currency has two minor units, and
`Money` is re-declared in three contexts that would all need the same answer. **Recommend the
team fix the scale in spec-03's `Money` definition.**

**F-2. spec-03 §2 and spec-01 §2.2 conflict for `sales-service`.**
"The application service orchestrates directly against JPA entities" cannot hold at the same time
as "presentation → application → domain; infrastructure → domain", because the JPA entities
cannot live in `domain` and `application` may not depend on `infrastructure`. Resolved in favour
of §2.2 (see **V-2**), but the conflict is in the specification and should be settled in the
text rather than left to each implementer.

**F-3. `supplierRef` is accepted and then discarded.**
spec-04's `CreateBatchRequest` carries it and spec-03 §1 models a `GoodsReceipt` entity
(`receiptId`, `batchId`, `receivedAt`, `supplierRef`) to hold it, but no endpoint returns it, no
test covers it, and `BatchResponse` has no field for it. Rather than persist a second entity
nothing reads, the field is currently dropped. It is a real gap in FR1 — "Register goods
receipt" — and `GoodsReceipt` should be built when something needs to read it. Flagged so it is
not mistaken for an oversight.

**F-4. `PriceRule` has no category-level margin floor.**
spec-03 §3 already records this as open: FR8 requires floors "per SKU **and** per category" and
only the SKU-level floor is modelled, with no precedence rule. Week 7. Restated here only
because `GET /api/prices/{sku}` now returns `marginFloorRatio` and a reader might assume the
requirement is met.
